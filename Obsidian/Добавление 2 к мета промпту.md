## **🔧 ДОПОЛНЕНИЕ №2 К СПЕЦИФИКАЦИИ «NPK-CALC-FACTORY»**

### **Цель:**
Предоставить Мета-Архитектору **конкретные, измеримые требования** для генерации промптов, которые обеспечат **детерминированную работу, лёгкое управление и защиту от ошибок интерпретации**.

### **1. СТАНДАРТ ВЫВОДА ДЛЯ СОЗДАЮЩИХ АГЕНТОВ (Агенты 1-4)**
**(Интегрировать в раздел «ФОРМАТ ОТВЕТА АГЕНТА»)**

*   **Правило «Контейнер для передачи»:** Весь созданный артефакт (план, дизайн, ТЗ-Х, код), который должен быть передан следующему агенту или проверке, **обязательно помещается внутрь специальных маркеров**.
*   **Требуемый формат ответа:**
    ```
    ОТ: [Имя агента]
    ВЫПОЛНЕНО: [Да/Нет]
    СТАТУС: [✅ УСПЕХ / ⚠️ ПРЕДУПРЕЖДЕНИЕ / ❌ ОШИБКА]

    [Служебные рассуждения, анализ, пояснения могут быть здесь...]

    ---НАЧАЛО БЛОКА ДЛЯ ПЕРЕДАЧИ---
    [ЧИСТЫЙ АРТЕФАКТ, ГОТОВЫЙ К ПЕРЕДАЧЕ.
     ТОЛЬКО план, дизайн, ТЗ-Х или код.
     Без лишних комментариев.]
    ---КОНЕЦ БЛОКА ДЛЯ ПЕРЕДАЧИ---

    СЛЕДУЮЩИЙ ШАГ:
    ...
    ```
*   **Инструкция для дирижёра:** *«После получения ответа от создающего агента, дирижёр копирует ВЕСЬ текст МЕЖДУ строками `---НАЧАЛО БЛОКА...` и `---КОНЕЦ БЛОКА...` (включая эти строки) и вставляет его как ВХОДНЫЕ ДАННЫЕ для следующего агента в цепочке.»*

### **2. СТАНДАРТ ОБРАТНОЙ СВЯЗИ ДЛЯ КОНТРОЛЛЕРОВ И АРБИТРА (Агенты 5-8)**
**(Интегрировать в «Конкретную задачу» каждого контролирующего агента)**

*   **Правило «Инженерного отчёта об ошибке»:** Каждое замечание или ошибка при статусе ❌ **должны быть оформлены по строгому шаблону**. Это не «мнение», а **отчёт о несоответствии**.
*   **Требуемый формат описания каждой ошибки:**
    1.  **📍 МЕСТО ОШИБКИ:** Прямая цитата из проверяемого артефакта (1-2 строки).
    2.  **📚 НАРУШЕНИЕ:** Ссылка на документ, раздел и пункт, который нарушен (например: «*Нарушено: Ошибки модуля 1, п.3.2 «Использовать FormData()»*»).
    3.  **🛠️ ИСПРАВЛЕНИЕ:** Конкретное, исполняемое действие (например: «*Заменить строку `const params = new URLSearchParams(formData);` на `const fd = new FormData(formElement);`*»).
    4.  **🔍 ПРИЧИНА:** Краткое техническое или логическое обоснование (например: «*Использование URLSearchParams с бинарными данными FormData может привести к некорректной кодировки, FormData — стандартный способ.*»).

### **3. ТРЕБОВАНИЕ К ДЕТАЛИЗАЦИИ «ИСТОЧНИКОВ ИСТИНЫ» В ПРОМПТАХ**
*   **Правило:** В разделе промпта «ТВОИ ИСТОЧНИКИ ИСТИНЫ (ДОКУМЕНТЫ)» недостаточно просто перечислить названия файлов.
*   **Требование к Мета-Архитектору:** Для каждого агента он должен сгенерировать **краткую инструкцию по использованию каждого документа**, например:
    *   *Для NPK-Контроллер-Логики:* «Документ **ТЗ** — используй для проверки соответствия бизнес-целям (разделы 2, 3). Документ **БД** — используй ТОЛЬКО для проверки числовых констант, алгоритмов и табличных данных (таблицы `npk_constants`, `optimal_ranges`). Игнорируй в БД описания полей.»
    *   *Для NPK-Главный-Арбитр:* «Ты используешь **ВСЕ** документы. **ТЗ** — общие цели. **БД** — истинные данные. **Архитектура** — правила построения. **Ограничения** — технические запреты. **Ошибки модуля 1** — исторические уроки. **Инструкция проверки** — стандарты кода. Твоя задача — найти противоречие МЕЖДУ ними.»

### **4. ГРАДАЦИЯ ОШИБОК И СТАТУС ⚠️ (ПРЕДУПРЕЖДЕНИЕ)**
*   **Правило:** Не все отклонения являются блокирующими. В промптах контроллеров и арбитра необходимо явно разделить ошибки на **КРИТИЧЕСКИЕ** и **НЕЗНАЧИТЕЛЬНЫЕ**.
*   **Требования к Мета-Архитектору:**
    1.  На основе документов (особенно «Ошибки модуля 1», «Инструкция проверки») составить для каждого контроллера **два списка**.
    2.  **Критические ошибки:** Нарушения, которые делают артефакт непригодным (неверный алгоритм, нарушение безопасности, архитектурное нарушение). Наличие ХОТЯ БЫ ОДНОЙ критической ошибки = статус **❌**.
    3.  **Незначительные ошибки:** Отклонения от стандартов, не влияющие на функциональность (стиль кода, опечатки в комментариях, мелкие formatting issues). Если есть ТОЛЬКО незначительные ошибки = статус **⚠️ ПРЕДУПРЕЖДЕНИЕ**.
    4.  **Формат вывода при ⚠️:** В блоке «АНАЛИЗ И ОБОСНОВАНИЕ» перечислить все незначительные ошибки. В «СЛЕДУЮЩИЙ ШАГ» указать: *«Артефакт МОЖЕТ быть передан на утверждение Главному Арбитру (Агенту 5), но рекомендуется исправить замечания. Решение о передаче дальше принимает только Главный Арбитр.»*

### **5. СКРИПТ ПЕРЕДАЧИ УПРАВЛЕНИЯ ПРИ УСПЕХЕ (✅)**
*   **Правило:** Промпт каждого агента должен заканчиваться **готовой, копируемой фразой**, которую дирижёр может использовать для передачи артефакта следующему агенту.
*   **Требуемая формулировка (в разделе «СЛЕДУЮЩИЙ ШАГ» при статусе ✅):**
    > **СЛЕДУЮЩИЙ ШАГ:**
    > Артефакт утверждён. **Дирижёр, скопируй весь блок между `---НАЧАЛО БЛОКА...` и `---КОНЕЦ БЛОКА...` из этого сообщения и отправь его в чат `[Имя следующего агента]` со следующим заданием:**
    > ```
    > ЗАДАЧА ДЛЯ: [Имя следующего агента]
    > КОНТЕКСТ: [Указать контекст, например: "Разработка на основе Утверждённого Плана"]
    > ВХОДНЫЕ ДАННЫЕ: [Указать, что передаётся, например: "Утверждённый План (в приложенном блоке)"]
    > ЗАДАНИЕ: [Стандартная задача для этого агента из спецификации]
    > ```

### **6. СТАНДАРТИЗАЦИЯ СТИЛЯ И ТОНА ВСЕХ ПРОМПТОВ**
*   **Правило:** Все 8 промптов должны быть написаны в **едином, императивном, безличном стиле** для максимальной предсказуемости.
*   **Конкретные требования к Мета-Архитектору:**
    *   **Настроение:** Инструкция, приказ, протокол. Никаких «привет», «пожалуйста», «мог бы».
    *   **Наклонение:** Повелительное («Сделай», «Проверь», «Сравни», «Верни»). Избегать сослагательного («было бы хорошо»).
    *   **Фокус на действии:** Каждое предложение в промпте должно описывать **конкретное действие** агента или **конкретное правило**.
    *   **Запрет на философию:** Не объяснять агенту «зачем нужна система» или «почему важно качество». Только **ЧТО ДЕЛАТЬ**.
