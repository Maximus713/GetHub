# **ТЕХНИЧЕСКОЕ ЗАДАНИЕ**
## **На развитие системы автоматизированного аудита и рефакторинга кода**

---

## **1. КОНЦЕПЦИЯ ПРОЕКТА**

### **1.1. Идея (Core Concept)**
Создать **модульную систему промптов**, которая:
- Анализирует код на наличие реальных, критических ошибок
- Исключает ложные срабатывания (главная проблема текущей системы)
- Вносит минимальные, безопасные исправления
- Гарантирует, что код остаётся работоспособным
- Останавливается, когда код чист (а не ищет "идеал")

### **1.2. Философия системы**
```
"Лучше пропустить 10 неочевидных проблем, чем создать 1 ложное срабатывание
и сломать рабочий код."
```

### **1.3. Ключевой инсайт из тестирования**
Исходная система страдала от **эскалации ложных срабатываний**:
- Проход 1: 10 "ошибок" → исправили → код работает
- Проход 2: 20 "ошибок" → исправили → код работает  
- Проход 3: 40 "ошибок" → исправили → код **перестал работать**

**Проблема:** Система не отличала реальные ошибки от субъективных "можно улучшить".

---

## **2. ТЕКУЩАЯ АРХИТЕКТУРА (уже создано)**

### **2.1. Последовательность промптов:**
```
0. КОНТРОЛЛЕР         → Анализ проекта, настройка стратегии
1. ДЕТЕКТОР           → Поиск ВСЕХ потенциальных проблем (без фильтрации)
2. ВАЛИДАТОР          → Фильтрация: оставить только РЕАЛЬНЫЕ ошибки
3. МИНИМАЛИСТ-ИСПРАВИТЕЛЬ → Консервативные, безопасные исправления
4. СТАБИЛИЗАТОР-ВЕРИФИКАТОР → Гарантии работоспособности
5. ФИНАЛЬНЫЙ ВЫВОД    → Отчёт + исправленный код
```

### **2.2. Ключевые инновации текущей системы:**

#### **A. Разделение "поиска" и "валидации"**
- **Детектор** находит всё, но не фильтрует
- **Валидатор** доказывает, что проблема реальная
- Решает проблему субъективных оценок

#### **B. Система весов и порогов**
- Каждой проблеме присваивается "уверенность" (1-5)
- Жёсткие пороги для отсева ложных срабатываний
- Количественная оценка риска

#### **C. Принцип минимального вмешательства**
- Ограничение на количество исправлений за проход
- Проверка "снепшота" системы до/после
- Механизм мгновенного отката

#### **D. Чёткие критерии остановки**
- Когда код работает и нет критических ошибок → СТОП
- Нет бесконечного поиска "идеального кода"

## **3. ПРОБЛЕМЫ ДЛЯ РЕШЕНИЯ (что улучшить)**

### **3.1. Глобальные проблемы системы:**

#### **ПРОБЛЕМА 1: Отсутствие памяти системы**
- Система не запоминает историю проверок
- Не обучается на своих ошибках
- Каждый проход начинает "с чистого листа"

#### **ПРОБЛЕМА 2: Статичность критериев**
- Критерии валидации жёстко закодированы
- Не адаптируются под тип проекта
- Нет дифференциации: WordPress vs React vs API

#### **ПРОБЛЕМА 3: Нет реального тестирования**
- Проверка "в уме" (мысленное выполнение)
- Нет запуска реальных тестов
- Нет проверки производительности, памяти

#### **ПРОБЛЕМА 4: Ограничения контекста ChatGPT**
- Большие проекты не помещаются в контекст
- Потеря информации между промптами
- Нет persistence между сессиями

#### **ПРОБЛЕМА 5: Человеко-машинное взаимодействие**
- Нет интерфейса для ручного подтверждения
- Нельзя сказать "это ложное срабатывание, запомни"
- Нет incremental improvements

### **3.2. Конкретные технические проблемы:**

#### **А. В Детекторе:**
- Находит слишком много "потенциальных" проблем
- Нет приоритизации (важное vs косметика)
- Не использует статистику прошлых проверок

#### **Б. В Валидаторе:**
- Слишком строгий/слишком мягкий в зависимости от настроек
- Нет градаций между "точно ошибка" и "точно не ошибка"
- Не учитывает контекст проекта

#### **В. В Исправителе:**
- Слишком консервативный (может пропускать важные исправления)
- Нет системы "риск vs польза"
- Не оптимизирует последовательность исправлений

#### **Г. В Верификаторе:**
- Тестирование "в уме" ненадёжно
- Нет автоматических тестов
- Не проверяет нефункциональные требования (perf, security)

## **4. ЦЕЛИ РАЗВИТИЯ (Roadmap)**

### **4.1. Short-term (неделя):**

#### **Цель 1: Добавить систему обучения**
```
ЗАДАЧА: Система должна запоминать свои ошибки.

РЕШЕНИЕ:
1. После каждого аудита сохранять:
   - Какие проблемы были реальными
   - Какие были ложными срабатываниями
   - Какие исправления сломали код
   - Какие типы проверок ненадёжны

2. Использовать эти данные для:
   - Корректировки весов в Валидаторе
   - Настройки Детектора (что искать, что игнорировать)
   - Предсказания риска исправлений
```

#### **Цель 2: Дифференциация по типам проектов**
```
ЗАДАЧА: Разные проекты → разные критерии.

РЕШЕНИЕ:
1. Создать профили для:
   - WordPress плагины (безопасность, ABSPATH, nonce)
   - React SPA (состояние, перфоманс, bundle size)
   - API серверы (валидация, ошибки, logging)
   - Библиотеки (совместимость, документация)

2. Контроллер должен автоматически определять тип
3. Настраивать всю цепочку под тип проекта
```

#### **Цель 3: Улучшение Валидатора**
```
ЗАДАЧА: Меньше ложных срабатываний, больше реальных ошибок.

РЕШЕНИЕ:
1. Добавить "уровень доказательности":
   - Уровень 1: Есть воспроизводимый тест
   - Уровень 2: Нарушает конкретное правило из ТЗ
   - Уровень 3: "Возможно проблема" (игнорировать)

2. Внедрить перекрёстную проверку:
   - Два разных метода проверки одной проблемы
   - Если оба говорят "ошибка" → вероятно ошибка
   - Если расходятся → требуется ручная проверка
```

### **4.2. Medium-term (месяц):**

#### **Цель 4: Интеграция с реальными инструментами**
```
ЗАДАЧА: Заменить "проверку в уме" реальным тестированием.

РЕШЕНИЕ:
1. Для синтаксических проверок:
   - Использовать php -l, eslint, tsc --noEmit

2. Для тестирования функциональности:
   - Генерация минимальных unit-тестов
   - Мысленное выполнение критических сценариев

3. Для проверки безопасности:
   - Интеграция с известными уязвимостями (CVE)
   - Проверка на OWASP Top 10
```

#### **Цель 5: Система рисков и приоритетов**
```
ЗАДАЧА: Умное планирование исправлений.

РЕШЕНИЕ:
1. Матрица риска:
   - Ось X: Вероятность проблемы
   - Ось Y: Ущерб от проблемы
   - Ось Z: Стоимость исправления

2. Алгоритм планирования:
   - Сначала исправлять high probability × high impact
   - Потом low cost × high impact
   - Игнорировать high cost × low impact
```

#### **Цель 6: Многоуровневая архитектура**
```
ЗАДАЧА: Разные глубины аудита для разных нужд.

РЕШЕНИЕ:
1. Уровень 1: Быстрый аудит (5 мин)
   - Только критические ошибки
   - Только безопасность

2. Уровень 2: Стандартный аудит (15 мин)
   - Критические + важные ошибки
   - Безопасность + основные функции

3. Уровень 3: Глубокий аудит (30+ мин)
   - Полный анализ
   - Оптимизация, архитектура, стиль
```

### **4.3. Long-term (квартал):**

#### **Цель 7: Распределённая обработка**
```
ПРОБЛЕМА: Большие проекты не помещаются в контекст.

РЕШЕНИЕ:
1. Разбивать проект на модули
2. Анализировать каждый модуль отдельно
3. Собирать результаты
4. Анализировать межмодульные зависимости отдельно
```

#### **Цель 8: Коллаборативная система**
```
ЗАДАЧА: Участие человека в процессе.

РЕШЕНИЕ:
1. Интерфейс для подтверждения/отклонения проблем
2. Возможность добавить кастомные правила
3. Система feedback loop:
   - ИИ предлагает → человек подтверждает/отклоняет
   - ИИ учится на решениях человека
```

#### **Цель 9: Прогнозирование проблем**
```
ЗАДАЧА: Предсказывать будущие проблемы.

РЕШЕНИЕ:
1. Анализ паттернов:
   - "Если код имеет структуру X, то вероятны проблемы Y"
   - "Если исправить A, то может сломаться B"

2. Проактивные рекомендации:
   - "Эта архитектура может привести к проблемам масштабирования"
   - "Эти зависимости могут вызвать конфликты в будущем"
```

## **5. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ**

### **5.1. Требования к новым промптам:**

#### **Требование 1: Сохранение состояния**
```
Каждый промпт должен:
1. Принимать на вход результаты предыдущих этапов
2. Сохранять свои решения с обоснованиями
3. Передавать полную историю следующему промпту
```

#### **Требование 2: Конфигурируемость**
```
Система должна иметь:
1. Настраиваемые пороги (сколько ошибок искать)
2. Настраиваемые стратегии (консервативная/агрессивная)
3. Настраиваемые профили (WordPress/React/API)
```

#### **Требование 3: Обратная совместимость**
```
Новые версии промптов должны:
1. Работать с существующей цепочкой 0-1-2-3-4-5
2. Не ломать уже работающие сценарии
3. Постепенно улучшать, а не переписывать
```

### **5.2. Требования к интерфейсам:**

#### **Межпромптовое взаимодействие:**
```
ФОРМАТ ПЕРЕДАЧИ ДАННЫХ:
{
  "project_metadata": {...},
  "detection_results": [...],
  "validation_results": [...],
  "correction_plan": [...],
  "verification_results": {...},
  "learning_data": {...},
  "system_state": "READY_FOR_NEXT_STEP"
}
```

#### **Команды управления:**
```
СИСТЕМА КОМАНД:
- "START_AUDIT [project_type]" — начать новый аудит
- "CONTINUE_FROM [step]" — продолжить с шага
- "CHANGE_STRATEGY [strategy]" — сменить стратегию
- "ADD_CUSTOM_RULE [rule]" — добавить своё правило
- "MARK_AS_FALSE_POSITIVE [issue_id]" — пометить ложное срабатывание
```

## **6. МЕТРИКИ УСПЕХА**

### **6.1. Количественные метрики:**

#### **Метрика 1: Точность (Precision)**
```
precision = (реальные ошибки) / (все найденные "ошибки")

ЦЕЛЬ: > 90%
ТЕКУЩАЯ ПРОБЛЕМА: < 50% (много ложных срабатываний)
```

#### **Метрика 2: Полнота (Recall)**
```
recall = (найденные реальные ошибки) / (все реальные ошибки)

ЦЕЛЬ: > 80%
ПРИМЕЧАНИЕ: Лучше пропустить, чем создать ложное срабатывание
```

#### **Метрика 3: Стабильность (Stability)**
```
stability = (исправления не сломали код) / (все исправления)

ЦЕЛЬ: 100%
КРИТИЧЕСКИЙ ПОКАЗАТЕЛЬ: Нельзя ломать рабочий код
```

#### **Метрика 4: Эффективность (Efficiency)**
```
efficiency = (реальные ошибки исправлены) / (время работы)

ЦЕЛЬ: Улучшать со временем (система учится)
```

### **6.2. Качественные метрики:**

#### **Метрика 5: Полезность отчётов**
- Отчёт должен быть понятен разработчику
- Должны быть конкретные рекомендации
- Должны быть приоритеты (что делать сначала)

#### **Метрика 6: Предсказуемость системы**
- Разные запуски на одном коде должны давать сходные результаты
- Система не должна "сходить с ума" (10→20→40 ошибок)
- Критерии должны быть прозрачными

#### **Метрика 7: Адаптивность**
- Система должна работать с разными типами проектов
- Должна адаптироваться под конкретный код
- Должна учитывать историю проекта

## **7. ОГРАНИЧЕНИЯ И РИСКИ**

### **7.1. Ограничения платформы ChatGPT:**

#### **Ограничение 1: Контекстное окно**
- Максимум ~128K токенов
- Большие проекты не помещаются
- **Решение:** Разбивать на модули, использовать суммаризацию

#### **Ограничение 2: Отсутствие persistence**
- Нет сохранения состояния между сессиями
- **Решение:** Сохранять состояние в промптах, передавать явно

#### **Ограничение 3: Нет выполнения кода**
- Нельзя запустить тесты
- **Решение:** Мысленное выполнение + генерация тестов для разработчика

### **7.2. Технические риски:**

#### **Риск 1: Переобучение**
Система может стать слишком специфичной для определённых проектов.
**Митигация:** Регулярная валидация на новых типах проектов.

#### **Риск 2: Излишняя сложность**
Система может стать слишком сложной для понимания.
**Митигация:** Принцип KISS, модульность, документация.

#### **Риск 3: Ложная уверенность**
Разработчики могут слишком доверять системе.
**Митигация:** Чёткие предупреждения, "требует ручной проверки".

## **8. ПРИНЦИПЫ РАЗРАБОТКИ**

### **8.1. Основные принципы:**

#### **Принцип 1: Безопасность прежде всего**
```
"Никогда не сломать рабочий код" — абсолютный приоритет.
Лучше не исправить, чем сломать.
```

#### **Принцип 2: Постепенное улучшение**
```
Не пытаться создать идеальную систему сразу.
Итеративный подход: запустить → измерить → улучшить.
```

#### **Принцип 3: Прозрачность и объяснимость**
```
Каждое решение системы должно быть объяснимо.
"Почему это ошибка?" → "Потому что нарушает правило X в строке Y".
```

#### **Принцип 4: Фокус на реальных проблемах**
```
Игнорировать косметику, сосредоточиться на:
1. Безопасность
2. Критические ошибки
3. Основная функциональность
```

### **8.2. Принципы дизайна промптов:**

#### **Единая структура данных**
```
Все промпты работают с единым форматом:
1. Вход: предыдущее состояние + команда
2. Обработка: алгоритм + обучение
3. Выход: новое состояние + отчёт
```

#### **Изоляция ответственности**
```
Каждый промпт делает ОДНУ вещь хорошо:
- Детектор только ищет
- Валидатор только фильтрует
- Исправитель только исправляет
- Верификатор только проверяет
```

#### **Возможность обхода (bypass)**
```
Для особых случаев должна быть возможность:
- Пропустить этап
- Принудительно принять решение
- Добавить кастомное правило
```

## **9. ТЕСТОВЫЕ СЦЕНАРИИ ДЛЯ ВАЛИДАЦИИ**

### **9.1. Базовые тесты:**

#### **Тест 1: Простой WordPress плагин**
```
ЦЕЛЬ: Проверить базовую функциональность
КОД: Плагин с 10 файлами, без ABSPATH проверок
ОЖИДАНИЕ: Найдёт отсутствие ABSPATH, предложит исправление
```

#### **Тест 2: Проект с ложными срабатываниями**
```
ЦЕЛЬ: Проверить фильтрацию
КОД: Проект с "плохой" архитектурой, но работающий
ОЖИДАНИЕ: Не найдёт "ошибок" в работающем коде
```

#### **Тест 3: Каскадные исправления**
```
ЦЕЛЬ: Проверить стабильность
КОД: Проект, где исправление A ломает B
ОЖИДАНИЕ: Система обнаружит проблему, откатит или предупредит
```

### **9.2. Продвинутые тесты:**

#### **Тест 4: Обучение на истории**
```
ЦЕЛЬ: Проверить систему обучения
ШАГИ:
1. Запустить аудит, пометить некоторые проблемы как ложные
2. Запустить аудит снова на том же коде
3. Проверить, что ложные срабатывания исчезли
```

#### **Тест 5: Адаптация к типу проекта**
```
ЦЕЛЬ: Проверить дифференциацию
ШАГИ:
1. Запустить на WordPress плагине → должен искать ABSPATH
2. Запустить на React SPA → должен искать state management issues
3. Проверить разные чек-листы
```

#### **Тест 6: Большой проект**
```
ЦЕЛЬ: Проверить масштабируемость
КОД: Проект с 100+ файлами
ОЖИДАНИЕ: Система должна работать, возможно с суммаризацией
```

## **10. КОНТАКТНЫЕ ТОЧКИ С ПОЛЬЗОВАТЕЛЕМ**

### **10.1. Что должен вводить пользователь:**

#### **Минимальный ввод:**
```
1. Код проекта (все файлы)
2. Команда: "ПРОАНАЛИЗИРУЙ И ИСПРАВЬ КРИТИЧЕСКИЕ ОШИБКИ"
```

#### **Расширенный ввод:**
```
1. Код проекта
2. Тип проекта (опционально)
3. Стратегия (консервативная/агрессивная)
4. История предыдущих аудитов (опционально)
5. Кастомные правила (опционально)
```

## **12. РЕЗЮМЕ ДЛЯ РАЗРАБОТЧИКА ПРОМПТОВ**

### **Ключевые моменты для понимания:**

1. **Главная проблема текущей системы** — эскалация ложных срабатываний (находит всё больше "ошибок" в уже исправленном коде)

2. **Ключевое решение** — разделение на Детектор (находит всё) и Валидатор (доказывает, что ошибка реальная)

3. **Философия** — "лучше пропустить реальную ошибку, чем создать ложную и сломать код"

4. **Цель развития** — сделать систему умнее, но безопаснее

5. **Метрика успеха** — precision > 90%, stability = 100%

### **Что улучшать в первую очередь:**

1. **Добавить память системы** — чтобы не повторять одни и те же "ошибки"
2. **Дифференциация по типам проектов** — WordPress ≠ React ≠ API
3. **Улучшить валидацию** — меньше ложных срабатываний
4. **Добавить реальное тестирование** (хоть и мысленное)

### **Чего избегать:**

1. **Не усложнять без нужды** — система должна оставаться понятной
2. **Не снижать безопасность** — никогда не ломать рабочий код
3. **Не терять объяснимость** — каждое решение должно быть понятно
4. **Не создавать бесконечные циклы** — система должна останавливаться

---

**Итог:** Мы строим не "идеальный анализатор кода", а **надёжного помощника**, который находит реальные проблемы и безопасно их исправляет, не ломая работающий код.
