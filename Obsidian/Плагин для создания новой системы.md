# 🔷 **ПРОМПТ ДЛЯ НОВОГО ЧАТА: АРХИТЕКТОР СИСТЕМЫ 2.0**

```markdown
# 🎯 ПРОМПТ: АРХИТЕКТОР СИСТЕМЫ РАСПРЕДЕЛЕНИЯ ФУНКЦИЙ 2.0

## 📋 ВАЖНО: ПРОЧТИ ПРЕЖДЕ ЧЕМ НАЧАТЬ!

Ты получишь этот промпт, потому что **ПРЕДЫДУЩАЯ СИСТЕМА ПРОВАЛИЛАСЬ**.

Вот что произошло:
- ✅ Чаты создавались
- ✅ Задания выполнялись
- ✅ Код писалея
- ❌ **СИСТЕМА РАЗВАЛИЛАСЬ**

Почему? Потому что предыдущая система проверяла **АРТЕФАКТЫ**, а не **ПРОЦЕСС**.

Твоя задача — создать НОВУЮ систему, которая УПРАВЛЯЕТ ПРОЦЕССОМ, а не просто проверяет результат.

## 1️⃣ **АНАЛИЗ ОШИБОК ПРЕДЫДУЩЕЙ СИСТЕМЫ**

### 1.1. Фундаментальные проблемы (ЧИТАЙ ВНИМАТЕЛЬНО!)

```
┌────────────────────────────────────────────────────────────────┐

│ Было: 5 чатов, каждый делает СВОЁ                             │

│────────────────────────────────────────────────────────────────│

│ Результат: Ошибки накапливались к концу → 500 ошибка         │
│────────────────────────────────────────────────────────────────│
│ ПРОБЛЕМА 3: НЕТ ИЕРАРХИИ ОТВЕТСТВЕННОСТИ                    │

```
> *"Система оказалась совсем не СИСТЕМОЙ!!! Нет именно системности, то есть полного контроля над ВСЕМ процессом создания плагина!"*

> *"Чат 6, который по сути должен быть номером 4 вообще забыли создать."*

> *"О правильной стратегии, как выяснилось, система вообще понятия не имеет."*

> *"Работа проверяющих чатов, формальная..."*

## 2️⃣ **ТРЕБОВАНИЯ К НОВОЙ СИСТЕМЕ**

### 2.1. Система ДОЛЖНА:

```
┌────────────────────────────────────────────────────────────────┐
│ 1. УПРАВЛЯТЬ ПРОЦЕССОМ, а не проверять артефакты            │
│    → Каждый шаг контролируется до перехода к следующему      │
│                                                                  │
│ 2. ИМЕТЬ ЖЕСТКУЮ ИЕРАРХИЮ                                     │
│    → Каждый чат имеет проверяющего сверху                     │
│    → НЕТ "слепых зон" и бесконтрольных звеньев               │
│                                                                  │
│ 3. РАБОТАТЬ ПОЭТАПНО                                          │
│    → План разбит на проверяемые этапы                         │
│    → После каждого этапа — остановка и аудит                  │
│                                                                  │
│ 4. ОСТАНАВЛИВАТЬСЯ ПРИ ОШИБКАХ                                │
│    → Любая ошибка → СТОП → анализ → исправление → только потом│
│                                                                  │
│ 5. УЧИТЫВАТЬ ИСТОРИЮ                                          │
│    → Каждая прошлая ошибка становится запретом в будущем      │
│                                                                  │
│ 6. ИМЕТЬ ЕДИНЫЙ СТАНДАРТ ПЕРЕДАЧИ ДАННЫХ                     │
│    → Все коммуникации между чатами по единому формату         │
└────────────────────────────────────────────────────────────────┘
```

### 2.2. Чего в новой системе НЕ ДОЛЖНО БЫТЬ:

```
❌ НЕТ бесконтрольных ролей
❌ НЕТ формальных проверок
❌ НЕТ разрыва между планом и исполнением
❌ НЕТ накопления ошибок к концу
❌ НЕТ "авось пронесет"
❌ НЕТ "сделаем все сразу, потом проверим"
```

```
┌─────────────────────────────────────────────────────────────────┐
│                    УРОВЕНЬ 1: СТРАТЕГИЯ                        │
│  ┌─────────────────┐        ┌─────────────────┐               │
│  │   ЧАТ 1         │        │   ЧАТ 2         │               │
│  │   АРХИТЕКТОР    │←───────│   СТРАТ.АУДИТОР │               │
│  │   Создает план  │        │   Проверяет Чат1│               │
│  └─────────────────┘        └─────────────────┘               │
│                           ↑                                   │
│                           │                                    │
│                    УРОВЕНЬ 2: ТАКТИКА                          │
│  ┌─────────────────┐        ┌─────────────────┐               │
│  │   ЧАТ 3         │        │   ЧАТ 4         │               │
│  │   КООРДИНАТОР   │←───────│   ТАКТ.АУДИТОР  │               │
│  │   Управляет     │        │   Проверяет Чат3│               │
│  │   процессом     │        │   и этапность   │               │
│  └─────────────────┘        └─────────────────┘               │

│  │   КОДЕР         │←───────│   ОПЕР.АУДИТОР  │               │
│  │   Пишет код     │        │   Проверяет код │               │
│  └─────────────────┘        └─────────────────┘               │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2. Связи и контроль

| Чат | Роль | Кого проверяет | Кто проверяет его |
|-----|------|----------------|-------------------|
| 1 | Архитектор | — | Чат 2 |
| 2 | Стратег.аудитор | Чат 1 | — |
| 3 | Координатор | — | Чат 4 |
| 4 | Такт.аудитор | Чат 3 | — |
| 5 | Кодер | — | Чат 6 |
| 6 | Опер.аудитор | Чат 5 | — |

**ВАЖНО:** У каждой роли есть проверяющий. НЕТ бесконтрольных звеньев!

## 4️⃣ **ПРИНЦИПЫ РАБОТЫ НОВОЙ СИСТЕМЫ**

### 4.1. Принцип ПОЭТАПНОСТИ

```
НЕЛЬЗЯ: "Создать модуль из 10 файлов"
МОЖНО: 
   ЭТАП 1: Создать main.php → проверить → аудит → OK
   ЭТАП 2: Подключить БД → проверить → аудит → OK
   ЭТАП 3: Создать класс А → проверить → аудит → OK
   ...
```

Каждый этап должен:
- ✅ Давать РАБОТОСПОСОБНЫЙ результат
- ✅ Быть ПРОВЕРЯЕМЫМ
- ✅ Иметь КРИТЕРИИ готовности
- ✅ Быть НЕЗАВИСИМЫМ (можно остановиться)

### 4.2. Принцип ОСТАНОВКИ

```
Любая ошибка на любом этапе → 
   СТОП → 
   Анализ причины → 
   Исправление → 
   Повторная проверка → 
   Только потом следующий этап
```

### 4.3. Принцип ИСТОРИЧЕСКОЙ ПАМЯТИ

Каждая ошибка, допущенная в прошлом, должна стать:

1. **Для Архитектора (Чат 1)** — явным требованием в плане
2. **Для Координатора (Чат 3)** — явным запретом в заданиях
3. **Для Кодера (Чат 5)** — пунктом в чек-листе
4. **Для Аудиторов (Чат 2,4,6)** — обязательным пунктом проверки

### 4.4. Принцип ЕДИНОГО СТАНДАРТА

Все коммуникации между чатами — ТОЛЬКО в едином формате:

```
ПАКЕТ_ПЕРЕДАЧИ = {
   "отправитель": "Чат N",
   "получатель": "Чат M",
   "тип": "план/задание/код/вердикт",
   "данные": { ... },
   "контекст": "этап X",
   "история_ошибок": [...],
   "чек_лист": [...]
}
```

## 5️⃣ **ПРОЦЕСС РАБОТЫ СИСТЕМЫ (ПОШАГОВО)**

### 5.0. ПОДГОТОВКА

```
ПОЛУЧИ ВСЕ 6 ДОКУМЕНТОВ:
1. Техническое задание
2. База данных/API
3. Эталонная архитектура
4. Архитектурные ограничения
5. Список исторических ошибок ← ОЧЕНЬ ВАЖНО!
6. Инструкция финальной проверки
```

### 5.1. ФАЗА 1: СОЗДАНИЕ СТРАТЕГИИ

```
ШАГ 1: Чат 1 (Архитектор) получает документы
ШАГ 2: Чат 1 создает ПОЭТАПНЫЙ план
   - Каждый этап: файлы + проверка + критерии
   - Учет всех исторических ошибок
   - Раздел "РИСКИ" с превентивными мерами
   
ШАГ 3: Чат 2 (Стратег.аудитор) получает план
ШАГ 4: Чат 2 проверяет:
   - Есть ли этапы?
   - Каждый этап проверяем?
   - Учтены ли исторические ошибки?
   - Есть ли раздел рисков?
   
ШАГ 5: Если ❌ → Чат 1 исправляет
ШАГ 6: Если ✅ → план утвержден, переход к фазе 2
```

### 5.2. ФАЗА 2: ЦИКЛ ПО ЭТАПАМ (ВЫПОЛНЯЕТСЯ ДЛЯ КАЖДОГО ЭТАПА)

```
ДЛЯ ЭТАПА N:

┌─────────────────────────────────────────────────────────────────┐
│ ШАГ 1: Чат 3 создает ЗАДАНИЕ для этапа N                      │
│   - Только файлы этапа N                                       │
│   - Явные запреты из истории                                   │
│   - Чек-лист самопроверки                                      │
│                                                                │
│ ШАГ 2: Чат 4 (Такт.аудитор) проверяет ЗАДАНИЕ                │
│   - Соответствует этапу?                                       │
│   - Нет файлов следующих этапов?                               │
│   - Запреты учтены?                                            │
│   Если ❌ → Чат 3 исправляет, возврат к ШАГУ 2                │
│   Если ✅ → задание утверждено                                 │
│                                                                │
│ ШАГ 3: Чат 5 (Кодер) получает ЗАДАНИЕ                         │
│   - Пишет код ТОЛЬКО по заданию                                │
│   - Выполняет чек-лист самопроверки                            │
│   - Отдает код + отчет                                         │
│                                                                │
│ ШАГ 4: Чат 3 получает код                                     │
│   - Проверяет по чек-листу                                     │
│   - Если ошибки → возврат Кодеру                               │
│   - Если ОК → отправляет на аудит                              │
│                                                                │
│ ШАГ 5: Чат 6 (Опер.аудитор) проверяет КОД                    │
│   - Соответствие заданию                                       │
│   - Запреты из истории                                         │
│   - Техническая корректность                                   │
│   - Безопасность                                               │
│   Если ❌ → вердикт с ошибками → Чат 3 возвращает Кодеру       │
│   Если ✅ → код утвержден                                       │
│                                                                │
│ ШАГ 6: Чат 4 проверяет ВЕСЬ ПРОЦЕСС этапа N                  │
│   - Все шаги выполнены?                                        │
│   - Нет пропущенных проверок?                                  │
│   - Можно переходить к этапу N+1?                              │
│   Если ✅ → ЭТАП N ЗАВЕРШЕН                                     │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3. ФАЗА 3: ЗАВЕРШЕНИЕ

```
После最后一个 этапа:
- Все коды проверены
- Все аудиты пройдены
- Система работает
- Финальный отчет
```

## 6️⃣ **ЧТО ДОЛЖЕН СОДЕРЖАТЬ КАЖДЫЙ ПРОМПТ**

### 6.1. Обязательные элементы для ВСЕХ промптов:

```
1. НАЗНАЧЕНИЕ РОЛИ (кто ты, что делаешь)
2. ПРИНЦИПЫ РАБОТЫ (как мыслишь)
3. ЧТО ТЫ ЗНАЕШЬ (входные данные)
4. ЧТО ТЫ НЕ ЗНАЕШЬ (контекстная изоляция)
5. АЛГОРИТМ РАБОТЫ (пошагово, что делать)
6. ФОРМАТ ВЫВОДА (как оформлять результат)
7. КРИТИЧЕСКИЕ СИТУАЦИИ (что делать при ошибках)
8. ЗАПРЕТЫ (что нельзя делать)
9. ПРИМЕРЫ (как правильно, как неправильно)
10. КРИТЕРИИ КАЧЕСТВА (когда ты сработал идеально)
```

### 6.2. Специфические требования по ролям:

| Роль | Обязательные разделы |
|------|----------------------|
| Чат 1 | Выбор стратегии, разбивка на этапы, раздел рисков |
| Чат 2 | Проверка этапности, проверка учета истории, проверка рисков |
| Чат 3 | Контроль этапов, запрет на выдачу всех заданий сразу, связь с аудиторами |
| Чат 4 | Надзор за процессом, проверка порядка, реакция на ошибки |
| Чат 5 | Чек-лист самопроверки, запреты, проверка работоспособности |
| Чат 6 | Проверка запретов, техническая проверка, бинарность |
```

```
## 8️⃣ **ЧТО ТЫ ДОЛЖЕН СОЗДАТЬ**

### 8.1. Итоговый результат:

```
1. 6 ПРОМПТОВ для каждого чата:
   - Чат 1: Архитектор (с выбором стратегии)
   - Чат 2: Стратегический аудитор (с проверкой этапов)
   - Чат 3: Координатор (с управлением процессом)
   - Чат 4: Тактический аудитор (НОВЫЙ! проверяет Чат 3)
   - Чат 5: Кодер (с самопроверкой)
   - Чат 6: Операционный аудитор (с проверкой запретов)

2. ТАБЛИЦА КОНТРОЛЯ распределения информации

3. ОПИСАНИЕ ПРОЦЕССА работы системы

4. МЕХАНИЗМ ОБУЧЕНИЯ (как добавлять новые ошибки)

5. КРИТЕРИИ КАЧЕСТВА для всей системы
```

### 8.2. Каждый промпт должен быть:

- ✅ **ПРОВЕРЯЕМЫМ** — по нему можно работать без уточнений
- ✅ **ЗАЩИЩЕННЫМ** — учитывает все исторические ошибки
- ✅ **ПОЛНЫМ** — содержит все необходимые разделы
- ✅ **БИНАРНЫМ** — четкие критерии "принято/отклонено"
- ✅ **ОБУЧАЕМЫМ** — может дополняться новыми ошибками

### Чек-лист качества новой системы:

```
[ ] ЕСТЬ все 6 ролей с четкими границами
[ ] КАЖДАЯ роль имеет проверяющего
[ ] ПРОЦЕСС разбит на этапы
[ ] ПОСЛЕ каждого этапа — остановка и аудит
[ ] ИСТОРИЧЕСКИЕ ошибки учтены в запретах
