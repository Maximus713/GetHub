---

## 🔄 **КОНТЕКСТ И ИСТОРИЯ РАЗРАБОТКИ**

### **ЧТО УЖЕ СДЕЛАНО:**
1. ✅ **Проанализированы ВСЕ 6 исходных документов** проекта NPK Calculators
2. ✅ **Разработана концепция системы** с 7 взаимосвязанными чатами-агентами
3. ✅ **Созданы 2 промпта** из 7:
   - **NPK-АРХИТЕКТОР** (полный, детальный, ~1500 слов)
   - **КОНТРОЛЛЕР АРХИТЕКТУРЫ** (исправленная версия, ~1500 слов)
4. ✅ **Установлены принципы работы**, выявлены критические ошибки и найдены решения

### **КЛЮЧЕВОЕ ДОСТИЖЕНИЕ:**
Мы создали **систему распределенных незаинтересованных контроллеров**, где:
- Каждый агент делает ТОЛЬКО свою работу
- Контроллеры — объективные арбитры (не создают контент)
- Ошибки обнаруживаются на том же уровне, где созданы
- Система самокорректирующаяся

## 🏗️ **ФИЛОСОФИЯ И ПРИНЦИПЫ СИСТЕМЫ**

### **🎯 ЦЕЛЬ СИСТЕМЫ:**
Создать **практически безошибочный процесс разработки** WordPress плагина, где неправильное понимание **физически не может** привести к неправильному результату.

### **⚡ 4 КРИТИЧЕСКИХ ПРИНЦИПА:**

#### **1. ПРИНЦИП НЕЗАИНТЕРЕСОВАННОСТИ КОНТРОЛЛЕРОВ**
```
Контроллеры НЕ создают контент
Контроллеры НЕ заинтересованы в "проталкивании" работы
Контроллеры — объективные арбитры с вето-правом
→ Это главный защитный механизм системы
```

#### **2. ПРИНЦИП УЗКОЙ СПЕЦИАЛИЗАЦИИ**
```
Каждый чат делает ТОЛЬКО свою работу
Не пытается делать работу других
Имеет четкие границы ответственности
→ Это предотвращает "расплывание" контекста
```

#### **3. ПРИНЦИП МИНИМАЛЬНОЙ ИНФОРМАЦИИ**
```
Каждый чат получает ТОЛЬКО необходимые документы
Нет когнитивной перегрузки
Нет риска "забыть что-то важное среди 6 документов"
→ Каждый агент — эксперт в своей узкой области
```

#### **4. ПРИНЦИП РАННЕГО ОБНАРУЖЕНИЯ ОШИБОК**
```
Ошибка обнаруживается на том же уровне, где создана
Не накапливается технический долг
Стоимость исправления минимальна
→ Ошибка в плане исправляется изменением текста, не кода
```

#### **2. АРХИТЕКТОР** ✅ **ГОТОВ**
```
ЗАДАЧА: Превращать планы в архитектурный дизайн + контейнеры ТЗ-Х
ДОКУМЕНТЫ: Архитектура(вся), Ограничения(вся), Ошибки модуля 1(вся)

ВЫХОД: Дизайн → Контроллеру Архитектуры
КЛЮЧЕВОЙ ПРИНЦИП: "КАК и ИЗ ЧЕГО", не готовый код
```

#### **3. ДИСПЕТЧЕР ТЗ-Х**
```
ЗАДАЧА: Создавать детальные ТЗ-Х с заполняемыми шаблонами кода
ДОКУМЕНТЫ: ТЗ(4), Инструкция проверки(вся)
ВХОД: Контейнеры заданий от Архитектора (через Контроллер Архитектуры)
ВЫХОД: ТЗ-Х → Контроллеру Кода
КЛЮЧЕВОЙ ПРИНЦИП: Шаблоны с пропусками, не готовый код
```

#### **4. ИСПОЛНИТЕЛЬ КОДА**
```
ЗАДАЧА: Писать код по шаблонам ТЗ-Х
ДОКУМЕНТЫ: (Не видит оригиналов, только ТЗ-Х с шаблонами)
ВХОД: ТЗ-Х с заполняемыми шаблонами
ВЫХОД: Готовый код → Контроллеру Кода
КЛЮЧЕВОЙ ПРИНЦИП: Только заполнение пропусков в шаблонах
```

### **УРОВЕНЬ 2: КОНТРОЛЛИРУЮЩИЕ АГЕНТЫ (3 чата)**

#### **5. КОНТРОЛЛЕР ЛОГИКИ**
```
ЗАДАЧА: Проверять бизнес-логику на соответствие ТЗ и БД
ДОКУМЕНТЫ: ТЗ(2,4), БД(вся)
ПРОВЕРЯЕТ: Стратега (планы), может проверять логику в коде
ВЫХОД: `СТАТУС: ✅/❌` + ошибки + рекомендации
КРИТИЧЕСКИЕ ТОЧКИ:
- Алгоритм Отиаи: нормализация → минимумы → сумма × 100
- 0.45% ∈ optimal для влажного грунта (0.4-0.6)?
- Пороги из БД: 75% из get_constants()['thresholds']['min_match_percentage']
```

#### **6. КОНТРОЛЛЕР АРХИТЕКТУРЫ** ✅ **ГОТОВ**
```
ЗАДАЧА: Проверять архитектурный дизайн на соответствие документам
ДОКУМЕНТЫ: Архитектура(вся), Ограничения(вся)
ПРОВЕРЯЕТ: Архитектора (дизайн)
ВЫХОД: `СТАТУС: ✅/❌` + ошибки + рекомендации
КРИТИЧЕСКИЕ ТОЧКИ:
- Selection_Engine зависит только от NPK_Database::
- Нет вызовов из ядра (Engine) в UI классы
- Порядок WordPress хуков соблюден
- Классы в includes/, шаблоны в templates/
```

#### **7. КОНТРОЛЛЕР КОДА**
```
ЗАДАЧА: Проверять техническую корректность кода
ДОКУМЕНТЫ: Ошибки модуля 1(вся), Инструкция проверки(вся)
ПРОВЕРЯЕТ: Диспетчера (ТЗ-Х), Исполнителя (код)
ВЫХОД: `СТАТУС: ✅/❌` + ошибки + рекомендации
КРИТИЧЕСКИЕ ТОЧКИ:
- Имена файлов в kebab-case: class-selection-engine.php
- Нет статических стилей в JS (только динамические значения)
- AJAX через FormData(), а не URLSearchParams()
- Все CSS селекторы с префиксом .npk-
```

## ⚠️ **КРИТИЧЕСКИЕ НЮАНСЫ ИЗ НАШЕГО ОПЫТА**

### **🚨 ОШИБКИ, КОТОРЫЕ МЫ СОВЕРШИЛИ (НЕ ПОВТОРЯЙ!):**

#### **1. НЕСБАЛАНСИРОВАННОСТЬ ПРОМПТОВ**
- **Было:** Архитектор детальный (1500+ слов), Контроллер Архитектуры упрощенный (500 слов)
- **Стало:** ОБА промпта одинаково детальные (~1500 слов)
- **Принцип:** Все промпты должны быть **одинаковой мощности и детализации**

#### **2. НАРУШЕНИЕ РАСПРЕДЕЛЕНИЯ ДОКУМЕНТОВ**
- **Было:** Контроллер Архитектуры проверял "Учет ошибок модуля 1"
- **Проблема:** Контроллер НЕ ВИДИТ этот документ!
- **Исправление:** Контроллер проверяет ТОЛЬКО то, что указано в его документах

#### **3. ОТСУТСТВИЕ ПРИМЕРОВ**
- **Было:** Промпт без примеров правильной/неправильной работы
- **Стало:** Обязательные примеры для ✅ и ❌ случаев
- **Принцип:** Примеры — это **инструкция по применению** промпта

#### **4. НЕСОБЛЮДЕНИЕ СОБСТВЕННЫХ СТАНДАРТОВ**
- **Было:** Создали мета-промпт, но не следовали ему
- **Урок:** Мета-промпт — это **ЗАКОН**, а не рекомендация
- **Проверка:** Каждый созданный промпт должен проходить проверку по мета-промпту

### **✅ ЧТО СДЕЛАЛИ ПРАВИЛЬНО (ПОВТОРЯЙ!):**

#### **1. ДЕТАЛЬНЫЕ ЧЕК-ЛИСТЫ**
Каждый контроллер имеет **конкретные пункты проверки** с:
- Точными формулировками
- Ссылками на документы (Архитектура §2.1)
- Примерами правильного/неправильного

#### **2. САМОДОСТАТОЧНОСТЬ**
Промпт содержит ВСЕ, что нужно агенту:
- Что делать
- Что не делать
- Какой формат входа/выхода
- Примеры работы
- Критерии самопроверки

#### **3. ЖЕСТКИЕ ФОРМАТЫ**
Форматы входа/выхода **однозначно парсятся**:
- Маркеры `---НАЧАЛО---` / `---КОНЕЦ---`
- Структурированные данные
- Четкие статусы ✅/❌

## ⚠️ **КРИТИЧЕСКИЕ ПРЕДУПРЕЖДЕНИЯ**

### **НЕДОПУСТИМО В ЛЮБОМ ПРОМПТЕ:**
1. **Смешение ролей:** Агент пытается делать работу других
2. **Избыточный контекст:** Видит документы, которые не нужны
3. **Нечеткий формат:** Выход нельзя однозначно распарсить
4. **Творчество у контроллеров:** Контроллер создает контент
5. **Пропуск проверок:** Нет чек-листа для самопроверки

### **ОБЯЗАТЕЛЬНО В ЛЮБОМ ПРОМПТЕ:**
1. **Маркеры блока:** `---НАЧАЛО---` / `---КОНЕЦ---`
2. **Ссылки на документы:** При указании требований
3. **Примеры:** Оба случая (✅ и ❌)
4. **Обработка ошибок:** Протокол при получении ❌
5. **Запреты:** Четкий список "чего не делать"

## 🎯 **ТВОЯ ЗАДАЧА СЕЙЧАС:**

### **НЕМЕДЛЕННЫЕ ДЕЙСТВИЯ:**
1. **Создать оставшиеся 5 промптов** по шаблону выше
2. **Соблюдать баланс** — все промпты одинаково детальные
3. **Следовать мета-структуре** — 9 обязательных разделов
4. **Включать примеры** — для ✅ и ❌ случаев

### **ПРИОРИТЕТ ПОРЯДКА СОЗДАНИЯ:**
1. **Стратег** (нужен для запуска процесса)
2. **Контроллер Логики** (чтобы проверять Стратега)
3. **Диспетчер ТЗ-Х** (после Архитектора)
4. **Контроллер Кода** (чтобы проверять Диспетчера и Исполнителя)
5. **Исполнитель Кода** (последний в цепочке)

### **ПРОВЕРКА КАЖДОГО СОЗДАННОГО ПРОМПТА:**
Перед утверждением задай вопросы:
1. **Специализация:** Может ли этот агент быть заменен другим без потери?
2. **Контекст:** Не видит ли он лишних документов?
3. **Формат:** Можно ли автоматически распарсить его вывод?
4. **Интеграция:** Правильно ли стыкуется с предыдущим/следующим?
5. **Идемпотентность:** Даст ли одинаковый результат на одинаковый вход?

## 💡 **ФИНАЛЬНАЯ ФИЛОСОФИЯ:**

**Мы не надеемся, что чаты "всё правильно поймут".**  
**Мы создаём систему, где неправильное понимание ФИЗИЧЕСКИ НЕ МОЖЕТ привести к неправильному результату.**

Система построена так, что:
1. **Ошибка немедленно обнаруживается** независимым арбитром
2. **Исправляется на том же уровне**, где была допущена
3. **Не передаётся дальше** по цепочке
4. **Не накапливается** в виде технического долга

**Ты продолжаешь строительство этой системы. От твоей тщательности зависит, будет ли она работать.**
