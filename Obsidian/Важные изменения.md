### **ПОТЕНЦИАЛЬНЫЕ ОШИБКИ/ПРОБЛЕМЫ:**

1. **"Магическое число 10" для масштабирования** — Хотя это решение закреплено в ТЗ, оно требует:
   - Проверки, что все NPK культур в БД действительно нуждаются в таком масштабировании
   - Гарантии, что в будущем не появятся культуры с другим масштабом

2. **Жёсткая привязка к текущей структуре БД** — Если в БД:
   - Добавят 6-ю культуру — интерфейс не адаптируется автоматически
   - Изменят ключи фаз — модуль сломается

3. **Отсутствие `used_fallback` в примерах ответа** — В описании функций был этот флаг, в алгоритме он есть, но в примерах структуры ответа (п.4.5) его нет

4. **Дублирование CSS-переменных** — Указаны конкретные цвета (`#FFA500`, `#28a745`), но они же должны быть в CSS-файле — возможна рассогласованность

5. **Предположение о доступности `needs` в клиентских данных** — Для мгновенного обновления UI нужны данные культур, но не ясно, все ли они будут передаваться в `NPK_Fertilizer_Selector_Data`

### **СПОРНЫЕ РЕШЕНИЯ:**

1. **Отказ от клиентского предрасчёта** — В образце Модуля 1 была гибридная логика (клиентский preview + серверный точный расчёт). Здесь клиент только показывает загрузку. Это может ухудшить UX при медленном соединении.

2. **Фиксированные начальные значения** — Культура `tomato`, фаза `seedling` зашиты в ТЗ, хотя в БД они могут измениться.

3. **Сложность алгоритма подсказок** — Проверка "фаза === 'Вегетация'" зависит от точного совпадения строк, что чувствительно к изменениям в БД.

### **ЧТО МОЖНО БЫЛО СДЕЛАТЬ ЛУЧШЕ:**

1. **Более гибкое описание данных из БД** — Вместо "5 культур" указать "культуры из `get_crops()`", чтобы интерфейс адаптировался автоматически.

2. **Явное требование к структуре данных для JS** — Конкретный пример, какие данные из `get_crops()` должны попасть в `NPK_Fertilizer_Selector_Data`.

3. **Тестовые сценарии** — Добавить раздел "Примеры работы" с конкретными входными данными и ожидаемыми результатами.

4. **Обработка edge cases** — Что делать, если в БД нет удобрений вообще? Если NPK культуры = [0,0,0]?

### 🔴 **1. СЛАБЫЕ МЕСТА В БИЗНЕС-ЛОГИКЕ / UX**

**А. Риск "пустого результата" при высоком пороге**
*   **Проблема:** Порог 75% может оказаться слишком высоким для нишевых культур или фаз. Если ни одно удобрение не проходит порог, показываем "лучшее из плохих" (например, 65%). Пользователь видит низкий процент → теряет доверие к системе.
*   **Решение:** 
    *   **Или** сделать порог адаптивным (снижать, если нет результатов).
    *   **Или** всегда показывать топ-3, но цветовой индикацией (красный/желтый/зеленый) явно обозначать, что результат "неидеальный".
    *   **Или** добавить текст-пояснение: "Идеального совпадения не найдено. Рекомендуем наиболее близкий вариант".

**Б. Недокументированная обработка нулей в NPK**
*   **Проблема:** В примере есть удобрение `0-52-34`. Ноль в азоте. Алгоритм Отиаи с нормализацией может дать некорректный результат при сравнении `[10,15,30]` с `[0,52,34]`. Вектор с нулем плохо поддается нормализации.
*   **Решение:** Нужно явно прописать в ТЗ, как обрабатываются нули: 
    *   Добавлять минимальную эпсилон-величину (0.001) ко всем значениям перед нормализацией?
    *   Использовать другую метрику для случаев с нулями?

**В. Статичность данных (культуры/фазы)**
*   **Проблема:** Списки культур и фаз зашиты в код (5 культур, 4 фазы). Любое изменение требует правок программиста.
*   **Решение:** Вынести в ту же БД (таблицу `cultures` и `phases`) или в конфигурационный файл, который можно редактировать через админ-панель.

### 🏗️ **2. АРХИТЕКТУРНЫЕ РИСКИ (СИСТЕМНЫЕ)**

**А. Конфликт источников данных (JSON vs PHP БД)**
*   **Проблема:** В одном описании — JSON-файлы, в другом — общая БД PHP. Это фундаментальное расхождение.
*   **Решение:** **Необходимо жесткое решение.** Я强烈но建议 использовать **БД**:
    1.  Это соответствует архитектуре "общих ресурсов" из системного промпта.
    2.  Данные проще редактировать через админку WordPress (через кастомные таблицы или плагин типа ACF).
    3.  Легче кешировать.
    *   **В ТЗ нужно явно указать:** "Все данные берутся из общей БД `npk-database.php`. JSON-файлы из описания — это пример структуры таблиц".

**Б. Производительность при росте базы удобрений**
*   **Проблема:** Алгоритм Отиаи требует перебора всех удобрений и математических операций для каждого. При 1000+ записей и частых AJAX-запросах может возникнуть нагрузка.
*   **Решение:** 
    *   Кеширование результатов запросов (пары "культура-фаза" → готовый JSON-ответ).
    *   Предварительный "грубый" фильтр (например, отсев удобрений, где все три значения NPK меньше целевых).
    *   В ТЗ заложить требование по времени отклика (< 300 мс).

**В. "Хрупкость" полей `priority` и `additives`**
*   **Проблема:** Они используются только для генерации текстовых подсказок. Это создает риск несогласованности: в `priority` может быть элемент `"B"`, а в `additives` он записан как `"Бор"`. Сравнение не сработает.
*   **Решение:** 
    *   Ввести жесткий **справочник микроэлементов** с кодами (`B`, `Ca`, `Fe`).
    *   В БД хранить коды, а не произвольные строки.
    *   В ТЗ явно прописать формат: "Поле `additives` содержит массив кодов в формате JSON: `["B","Ca"]`".

### 🖥️ **3. РИСКИ ИНТЕРФЕЙСА**

**А. Неочевидность выбора при одинаковом проценте**
*   **Проблема:** Два удобрения с совпадением 85%. Какое предпочесть? Алгоритм не дает ответа.
*   **Решение:** Ввести **вторичный критерий сортировки**: 
    1.  Наличие приоритетных добавок (больше совпадений с `priority` → выше).
    2.  Тип удобрения ("водорастворимое" выше "гранул", если не указано иное).

**Б. Отсутствие "состояния покоя"**
*   **Проблема:** При первом заходе на страницу не выбрана культура и фаза — что показывать? Пустой экран? Это плохой UX.
*   **Решение:** Показывать **инструкцию** или предлагать выбрать культуру. В ТЗ прописать начальное состояние интерфейса.

## **ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ В JS:**

```javascript
// Пример динамического создания кнопок культур
function createCultureButtons(cropsData, defaultCultureKey) {
    const container = document.querySelector('.culture-buttons-container');
    container.innerHTML = ''; // Очистить старые кнопки
    
    // Использовать crops_order или порядок ключей в объекте
    const cultureKeys = cropsData.crops_order || Object.keys(cropsData.crops);
    
    cultureKeys.forEach(cultureKey => {
        const culture = cropsData.crops[cultureKey];
        const button = document.createElement('button');
        button.type = 'button';
        button.classList.add('culture-button');
        button.dataset.cultureKey = cultureKey;
        button.textContent = culture.name;
        
        if (cultureKey === defaultCultureKey) {
            button.classList.add('active');
        }
        
        container.appendChild(button);
    });
}

// Пример динамического создания кнопок фаз
function createPhaseButtons(cropsData, selectedCultureKey, defaultPhaseKey) {
    const container = document.querySelector('.phase-buttons-container');
    container.innerHTML = '';
    
    const phases = cropsData.crops[selectedCultureKey]?.phases;
    if (!phases) return;
    
    const phaseKeys = Object.keys(phases);
    
    phaseKeys.forEach(phaseKey => {
        const phase = phases[phaseKey];
        const button = document.createElement('button');
        button.type = 'button';
        button.classList.add('phase-button');
        button.dataset.phaseKey = phaseKey;
        button.textContent = phase.name;
        
        if (phaseKey === defaultPhaseKey) {
            button.classList.add('active');
        }
        
        container.appendChild(button);
    });
}
```
