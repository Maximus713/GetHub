### ❌ **КРИТИЧЕСКОЕ НАРУШЕНИЕ: ДУБЛИРОВАНИЕ АЛГОРИТМА ОТИАИ В JS**

**Цитата из дополняющего ТЗ (B.1):**
> *«СТРОГО ЗАПРЕЩЕНО: повторять или "зеркалить" бизнес-логику и формулы Calculation_Engine в JavaScript, или других PHP-классах».*

**Цитата из плана (раздел 2.6, `selector.js`):**
```javascript
// Алгоритм instant preview (клиентский):
// 1. Взять requirements[currentCropId][currentPhaseId].npk_normalized
// 2. Для каждого удобрения из fertilizers взять npk_normalized
// 3. Рассчитать min(a,b) по трём компонентам, сложить
// 4. Отфильтровать по >= threshold
// 5. Fallback: если <1 проходного → взять 3 лучших, пометить is_fallback: true
```

**Проблема:**  
План **полностью дублирует алгоритм Отиаи** на клиенте. Это прямое нарушение принципа **«Единый алгоритм — идентичен на клиенте и сервере»** (ТЗ, п. 1.1), но в сочетании с **ДТЗ B.1** это становится **архитектурной ошибкой**, а не технической деталью.

**Почему это нарушение стратегического уровня:**
- Создаёт **два источника истины** для одного и того же алгоритма.
- Алгоритм в JS **обязан** быть идентичным серверному, что:
  - делает невозможным изменение алгоритма без синхронного обновления JS;
  - создаёт риск рассинхронизации при обновлениях;
  - нарушает **абсолютный центр логики** (ДТЗ B.1).

**Правка:**  
В плане должно быть указано, что **instant preview** использует **упрощённую эвристику** (например, евклидово расстояние, скалярное произведение, косинусное сходство) — **ЛЮБОЙ метод, кроме полного копирования алгоритма Отиаи**.  
Текущая формулировка «Алгоритм Отиаи идентичен на клиенте и сервере» (ТЗ, п. 1.1) конфликтует с ДТЗ B.1, и **приоритет имеет дополняющее ТЗ (п. H)**.

### ⚠️ ЧАСТИЧНОЕ НАРУШЕНИЕ: ГРАНИЦА «БИЗНЕС-ЛОГИКА / UX-ЛОГИКА»

**Проблема:**  
План разрешает в JS:
- расчёт `match_percentage`
- fallback-отбор (3 лучших)
- фильтрацию по порогу

Согласно ДТЗ **B.2**, JS **МОЖЕТ** выполнять **упрощённый расчёт** для мгновенного UX, но **НЕ ИМЕЕТ ПРАВА** копировать алгоритм целиком и принимать решения, влияющие на итоговые данные.

**Текущая формулировка плана** описывает **точную копию серверного алгоритма**, что переводит JS из категории «UX-логика» в категорию «бизнес-логика».

**Требуемая правка:**  
Заменить «Алгоритм Отиаи» на «упрощённый алгоритм оценки сходства (например, евклидово расстояние или скалярное произведение)».  
Порог и fallback **НЕ ДОЛЖНЫ** применяться на клиенте — preview показывает **все** удобрения с нефильтрованной оценкой, либо отбор по упрощённой метрике, не претендующей на точность.

## ОБОСНОВАНИЕ ВЕРДИКТА

**План отклоняется по единственной, но критической причине:**

### ❌ Нарушение принципа «Абсолютный центр логики» (ДТЗ B.1)

План **явно и осознанно** размещает полную копию алгоритма Отиаи в JavaScript.  
Это нарушает:

1. **ДТЗ B.1** — «СТРОГО ЗАПРЕЩЕНО повторять или "зеркалить" бизнес-логику».
2. **ДТЗ F (Критерий неприёмки)** — «Реализация НЕ ПРИНИМАЕТСЯ, если JavaScript содержит логику выбора state / итоговых значений».
3. **ДТЗ H (Приоритет)** — дополняющее ТЗ имеет приоритет над основным.

**Почему это нельзя считать «технической деталью»:**
- Алгоритм Отиаи — **ключевая бизнес-логика модуля**.
- Его копирование в JS создаёт **два связанных, но независимо изменяемых источника истины**.
- Это нарушение **архитектурного паттерна**, а не кода.
- Даже если JS-версия идеально точна сегодня, **архитектура позволяет ей отличаться завтра**.

**Стратегический риск:**  
Система теряет свойство **«единственный источник истины»**.  
В будущем:
- Изменение алгоритма потребует синхронного обновления JS (не гарантировано);
- Появятся ситуации, когда preview и финальный ответ **будут расходиться**, что подорвёт доверие к интерфейсу;
- Будет нарушено фундаментальное требование **«Если завтра заменить JS — ничего не переписывается»** (эталонная архитектура, п. 5).
