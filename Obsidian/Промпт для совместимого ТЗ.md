# ПРОМПТ ДЛЯ СОЗДАНИЯ ТЕХНИЧЕСКОГО ЗАДАНИЯ КАЛЬКУЛЯТОРА ПОДБОРА УДОБРЕНИЙ

## КОНТЕКСТ ПРОЕКТА
Ты — технический писатель/архитектор, создающий ТЗ для второго модуля в семействе калькуляторов NPK. Уже существует и работает:

1. **Плагин:** `npk-calculators` (WordPress)
2. **Модуль 1:** `module-concentration/` — калькулятор концентрации растворов
3. **База данных:** `shared/config/npk-database.php` (обновлена полями `priority` и `additives`)

Тебе нужно создать ТЗ для **Модуля 2:** `module-fertilizer-selector/` — калькулятор подбора удобрений по составу NPK.

---

## КРИТИЧЕСКИЕ ТРЕБОВАНИЯ К ТЗ

### 1. АРХИТЕКТУРНАЯ СОВМЕСТИМОСТЬ (самое важное!)
ТЗ должно гарантировать, что новый модуль:
- ✅ **Не ломает существующий модуль** `module-concentration/`
- ✅ **Использует ОБЩУЮ БД** без создания дублей
- ✅ **Самостоятельно регистрируется** в существующем плагине
- ✅ **Имеет уникальные имена** (шорткоды, хуки, классы)
- ✅ **Мифрирует структуру** первого модуля (папки `includes/`, `assets/`, `templates/`)

### 2. ПРЕДОТВРАЩЕНИЕ ТИПИЧНЫХ ОШИБОК
ТЗ должно явно запрещать:
- ❌ Создание нового `npk-calculators.php` (главный файл УЖЕ есть)
- ❌ Создание новой БД (БД УЖЕ есть в `shared/config/`)
- ❌ Изменение файлов первого модуля
- ❌ Конфликты имён классов/функций
- ❌ Использование `URLSearchParams()` и других запрещённых конструкций из ТЗ первого модуля

### 3. ЧЁТКАЯ ИЕРАРХИЯ ПРИОРИТЕТОВ
1. **Совместимость** с существующим плагином — абсолютный приоритет
2. **Функциональность** подбора удобрений
3. **UX/UI** компактность и наглядность
4. **Производительность** мгновенного отклика

---

## ТРЕБУЕМАЯ СТРУКТУРА ТЗ

### РАЗДЕЛ 1: ОДНОЗНАЧНЫЕ ИНСТРУКЦИИ ДЛЯ РАЗРАБОТЧИКА
- Контекст: "Это РАСШИРЕНИЕ существующего плагина"
- Проверка перед началом: список существующих файлов/папок
- Инструкция: "Создайте ТОЛЬКО папку `module-fertilizer-selector/` и её содержимое"
- Явные запреты с объяснением "почему"

### РАЗДЕЛ 2: АРХИТЕКТУРА И ИНТЕГРАЦИЯ
- Использование общей БД `NPK_Database::`
- Автозагрузка модуля (код-пример)
- Уникальные имена (таблица: что | префикс | пример)
- Взаимодействие с первым модулем (чего НЕ делать)

### РАЗДЕЛ 3: СПЕЦИФИКА ПОДБОРА УДОБРЕНИЙ
- Алгоритм сравнения пропорций (коэффициент Отиаи)
- Учёт полей `priority` и `additives`
- Порог соответствия ≥75%
- Генерация умных подсказок

### РАЗДЕЛ 4: ИНТЕРФЕЙС И UX
- Компактный табличный вид (одна строка = одно удобрение)
- Прогресс-бары соответствия с цветовой индикацией
- Автоматический пересчёт при выборе культуры/фазы
- Режим "топ-5 + показать все"

### РАЗДЕЛ 5: ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ
- Структура файлов (миррить `module-concentration/`)
- WordPress-интеграция (шорткод, хуки, AJAX)
- Форматы данных (JSON-ответы, AJAX-запросы через FormData)
- Обработка ошибок и отказоустойчивость

### РАЗДЕЛ 6: КРИТЕРИИ ПРИЁМКИ
- Работает ли первый модуль после установки второго?
- Нет ли конфликтов имён?
- Корректность алгоритмов подбора?
- Производительность и UX?

## КЛЮЧЕВЫЕ МОМЕНТЫ ДЛЯ АКЦЕНТА

### 1. "НЕ ИЗОБРЕТАТЬ ВЕЛОСИПЕД"
- Использовать те же подходы, что в первом модуле
- Те же паттерны кода, те же библиотеки (чистый JS, PHP 7.4+)
- Те же методы работы с WordPress

### 2. "ПРЕДУСМОТРЕТЬ БУДУЩЕЕ"
- Архитектура должна позволять добавление третьего модуля
- Общие ресурсы в `shared/`
- Каждый модуль в своей папке `module-*/`

### 3. "ЗАЩИТА ОТ ГЛУПЫХ ОШИБОК"
- Явные проверки в ТЗ: "Если видите X → делайте Y"
- Контрольные точки: "Перед отправкой файла проверьте..."
- Примеры кода для критических мест (автозагрузка, AJAX)

### 4. "ОДНОЗНАЧНОСТЬ И ПОНЯТНОСТЬ"
- Без сценариев "если/то" — только один путь
- Без противоречий между разделами
- Без технического жаргона без объяснений

## ФИНАЛЬНОЕ ЗАДАНИЕ

Создай **полное, детализированное ТЗ** для модуля подбора удобрений, которое:

1. **Гарантирует совместимость** с существующим плагином
2. **Исключает необходимость переделок** в будущем
3. **Позволяет легко добавить третий модуль**
4. **Содержит все необходимые технические детали**
5. **Понятно как разработчику, так и нетехническому специалисту**

**Объём:** Достаточно для начала разработки без дополнительных вопросов.

**Стиль:** Профессиональный, но с явными акцентами на критически важные моменты.

**Структура:** Логичная, с перекрёстными ссылками на общие части.

**Цель:** Разработчик, прочитав ТЗ, сразу понимает КАК делать и ЧТО НЕЛЬЗЯ делать.
