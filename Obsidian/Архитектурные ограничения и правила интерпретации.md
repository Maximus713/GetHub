## A. ЭТАЛОННЫЙ ПОТОК ДАННЫХ (НЕ ДОПУСКАЕТ ИНТЕРПРЕТАЦИЙ)

```
UI (JS)
  ↓
AJAX_Handler (PHP)
  ↓
Calculation_Engine (PHP)
  ↓

  ↓

  ↓

```

## B. ЖЁСТКОЕ РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ (БЕЗ ДОПУЩЕНИЙ)

### B.1. Calculation_Engine — абсолютный центр логики

`Calculation_Engine`:

- ✅ содержит **ВСЕ формулы**
    
- ✅ содержит **ВСЕ алгоритмы**
    
- ✅ определяет:
    
    - итоговую массу
        
    - итоговую концентрацию
        
    - итоговый `state`
        
    - итоговые предупреждения
        
- ✅ **ЕДИНСТВЕННЫЙ источник истины**
    

❌ **СТРОГО ЗАПРЕЩЕНО:**

- выносить любую часть логики расчёта или определения `state` за пределы `Calculation_Engine`
    
- повторять или "зеркалить" бизнес-логику и формулы Calculation_Engine в JavaScript, или других PHP-классах
    
- принимать решения в UI, влияющие на итоговые данные
    
РАЗРЕШЕНО:
— использовать переданные диапазоны state (ranges) для предварительного определения state в UI

---




### B.2. JavaScript (UI) — UX логика без бизнес-логики

JavaScript:
- ✅ **МОЖЕТ ДЛЯ UX:**
    - определять **предварительный `state`** по правилам п.4.3
    - сравнивать концентрацию с диапазонами для определения предварительного `state`
    - выполнять **упрощённый расчёт массы** для мгновенного отображения
    - интерполировать цвет внутри `state.range`
    - отображать предварительные данные до получения ответа сервера

- ❌ **НЕ ИМЕЕТ ПРАВА:**
    - изменять алгоритм определения `state` (правила п.4.3)
    - игнорировать финальный `state` с сервера
    - быть источником истины для финальных данных
    - принимать решения о безопасности

**Разрешённая логика для мгновенного UX:**
```js
// Для определения предварительного state (те же правила что и сервер)
function getPreviewState(concentration, profile) {
    for (let state of profile.states) {
        if (concentration >= state.range[0] && concentration < state.range[1]) {
            return state;
        }
    }
    return profile.states[profile.states.length - 1]; // последний state
}
```

### B.3. Data_Adapter — ТОЛЬКО подготовка данных для UI

`Data_Adapter`:

- ✅ используется **исключительно** для:
    
    - подготовки данных для `wp_localize_script`
        
    - приведения формата данных для отображения
        
- ✅ может применять валидацию **ТОЛЬКО для UI**
    
- ❌ **НЕ ИМЕЕТ ПРАВА:**
    
    - участвовать в расчётах
        
    - передавать данные в `Calculation_Engine`
        
    - определять `state`
        
    - участвовать в AJAX
        
    - быть частью цепочки расчёта
        

B.4. Элементы слайдера: чёткое разделение

**НА МЕТКЕ НАД СЛАЙДЕРОМ (допустимо):**
✅ Текст названия состояния ("Оптимальная", "Опасная" и т.д.)
✅ Фон цвета состояния
✅ Контрастный цвет текста для читаемости

**НА САМОМ СЛАЙДЕРЕ/ПОД НИМ (допустимо):**
✅ Числовые метки минимального/максимального значения (0.05%, 1.50%)
✅ Промежуточные числовые метки (0.78% и другие)
✅ Сплошная одноцветная заливка слайдера (цвет текущего состояния)

**ЗАПРЕЩЕНО В ЛЮБОМ МЕСТЕ НА/ВОКРУГ СЛАЙДЕРА:**
❌ Эмодзи состояний (✅, ⚠️, ❌) - они только в блоке результатов
❌ Цветовая сегментация слайдера (разные цвета для разных зон)
❌ Границы между состояниями на слайдере
❌ Описания состояний или рекомендации
---



**B.5. Прозрачность расчётов: две концентрации**

**ОБЯЗАТЕЛЬНО:**
✅ Показывать ОБЩУЮ концентрацию (все растворённые вещества)
✅ Показывать концентрацию ТОЛЬКО по NPK (расчётное значение)
✅ Обновлять NPK концентрацию при смене удобрения
✅ Чётко подписывать оба поля

**ЗАПРЕЩЕНО:**
❌ Позволять редактировать поле "Концентрация NPK"
❌ Использовать NPK концентрацию для расчёта массы или определения состояния
❌ Скрывать разницу между общей и NPK концентрацией

**Обоснование:** Пользователь должен понимать, что:
1. Он задаёт ОБЩУЮ концентрацию раствора
2. Активная часть (NPK) составляет только часть от общей
3. Риски (состояния) определяются по ОБЩЕЙ концентрации



## ПРАВИЛО ДВУХУРОВНЕВОГО STATE
#### C.1. Источники состояния

- **ФИНАЛЬНЫЙ `state`** ВСЕГДА определяется:
    - только в `Calculation_Engine`
    - только на сервере
    - является источником истины для всех итоговых данных

- **ПРЕДВАРИТЕЛЬНЫЙ `state`** может определяться:
    - в JavaScript для мгновенного UX
    - по ТЕМ ЖЕ правилам, что и финальный (п.4.3)
    - заменяется финальным при получении ответа сервера

- UI **ОТОБРАЖАЕТ:**
    - предварительный `state` для мгновенной обратной связи
    - финальный `state` как подтверждённый результат

✅ Определение предварительного `state` в UI — разрешено для UX
❌ Игнорирование финального `state` — ошибка реализации

## D. ЖЁСТКАЯ ИНТЕРПРЕТАЦИЯ ЛОКАЛЬНОГО РАСЧЁТА

### D.1. Что означает «локальный расчёт»

Локальный расчёт в UI:

- ✅ допустим **ТОЛЬКО** для:
    
    - предварительного отображения массы
        
    - анимации
        
    - мгновенной реакции интерфейса
        
- ❌ **НЕ ЯВЛЯЕТСЯ**:
    
    - расчётом результата
        
    - основанием для определения state
        
    - заменой серверного расчёта
        

**Окончательным считается ТОЛЬКО результат, полученный через AJAX.**

## E. ПРАВИЛО НЕПРОТИВОРЕЧИВОСТИ ФОРМУЛ

- Формула расчёта массы:
    
    - эталонная реализация — в `Calculation_Engine`
        
- Любая формула в JS:
    
    - считается **приближённой**
        
    - не обязана быть идентичной
        
    - не используется для принятия решений
        

---

## F. КРИТЕРИЙ НЕПРИЁМКИ (КРИТИЧЕСКИЙ)

Реализация **НЕ ПРИНИМАЕТСЯ**, если выполняется хотя бы одно условие:

- `state` определяется вне `Calculation_Engine`
    
- JavaScript содержит логику выбора `state`
    
- Data_Adapter участвует в расчётах
    
- Итоговые значения могут отличаться без AJAX
    
- В системе существует более одного «источника истины»
