**ПЕРЕБИРАЮ ВСЕ ВАРИАНТЫ:**

**Вариант 1: Архитектор создаёт чек-листы**
- Плюсы: Знает все требования, может создать полные чек-листы
- Минусы: Может упустить технические детали проверки

**Вариант 2: Разработчик создаёт чек-листы для своего кода**
- Плюсы: Знает код лучше всех
- Минусы: Субъективно, может упустить свои ошибки, противоречие интересов

**Вариант 3: Тестировщик сам создаёт чек-листы на основе ТЗ**
- Плюсы: Независимый взгляд, проверка именно по ТЗ
- Минусы: Может не понять нюансы реализации

**Вариант 4: Использовать готовые чек-листы из документа 6**
- Плюсы: Уже созданы, протестированы, учитывают ошибки модуля 1
- Минусы: Могут не покрыть специфику модуля 2

## **ПРАКТИЧЕСКИЙ ПРОЦЕСС:**

### **Шаг 1: Архитектор готовит чек-листы**
```
ИСХОДНЫЕ ДОКУМЕНТЫ:
1. Документ 6 (базовые чек-листы)
2. ТЗ модуля 2 (специфические требования)
3. Список ошибок модуля 1 (что избегать)

ДЕЙСТВИЯ:
1. Берет базовые чек-листы из документа 6
2. Добавляет проверки для алгоритма Отиаи
3. Добавляет проверки для Instant Preview
4. Добавляет проверки для fallback-режима
5. Создаёт контрольные точки для каждого файла

РЕЗУЛЬТАТ: Структурированные чек-листы для тестировщика
```

### **Шаг 2: Разработчик использует чек-листы**
```
Для каждого файла:
1. Перед созданием: смотрит чек-лист для этого типа файла
2. Во время создания: следует проверкам
3. После создания: выполняет самопроверку по чек-листу
4. Фиксирует: "Файл X проверен: [N]/[M] пунктов пройдено"
```

### **Шаг 3: Тестировщик выполняет чек-листы**
```
Получает:
1. Код модуля 2
2. Структурированные чек-листы от Архитектора
3. Дополнительные проверочные сценарии

Выполняет:
1. Проверяет каждый файл по чек-листу
2. Выполняет интеграционные тесты
3. Создаёт отчёт
```

## **КОНКРЕТНЫЙ ПРИМЕР ЧЕК-ЛИСТА ДЛЯ МОДУЛЯ 2:**

```
[ ] 3. Генерация подсказок
    [ ] Только при additives ∩ priority ≠ ∅
    [ ] Формат: "Содержит [элемент], важный для [фаза]"

[ ] 4. Цвета прогресс-баров
    [ ] Зелёный ≥ 85%
    [ ] Оранжевый 75-84%
    [ ] Серый < 75%
```
