## **🏗️ ЧАСТЬ 1: ПОЛНАЯ АРХИТЕКТУРА СИСТЕМЫ №5**

### **1.1. ПЯТЬ РОЛЕЙ СИСТЕМЫ (иерархия и назначение)**

Система состоит из 5 изолированных ролей, расположенных по уровням абстракции:

#### **УРОВЕНЬ 1: СТРАТЕГИЧЕСКИЙ (макро)**
```
🔷 РОЛЬ 1: АРХИТЕКТОР (STRATEGIST)
Назначение: Преобразование ТЗ в архитектурный план
Абстракция: "ЧТО должно быть построено?"
Контекстная изоляция: НЕ знает об ошибках реализации, ограничениях кодирования
```

```
🟢 РОЛЬ 2: СТРАТЕГИЧЕСКИЙ АУДИТОР (STRATEGIC AUDITOR)  
Назначение: Проверка архитектурных планов на глобальном уровне
Абстракция: "ПРАВИЛЬНО ЛИ мы решили что построить?"
Контекстная изоляция: НЕ знает о проблемах кода, технических ограничениях
```

#### **УРОВЕНЬ 2: ТАКТИЧЕСКИЙ (мезо)**
```
🔶 РОЛЬ 3: КООРДИНАТОР (COORDINATOR)
Назначение: Преобразование планов в задания + контроль качества
Абстракция: "КАК мы будем это строить и проверять?"
Контекстная изоляция: НЕ знает о стратегических решениях, только о тактических ограничениях
```

#### **УРОВЕНЬ 3: ОПЕРАЦИОННЫЙ (микро)**
```
🟡 РОЛЬ 4: ОПЕРАЦИОННЫЙ АУДИТОР (OPERATIONAL AUDITOR)
Назначение: Техническая проверка готового кода
Абстракция: "ПРАВИЛЬНО ЛИ это построено технически?"
Контекстная изоляция: НЕ знает об архитектурных решениях, стратегии проекта
```

```
🔵 РОЛЬ 5: КОДЕР (DEVELOPER)
Назначение: Точечное выполнение конкретных заданий
Абстракция: "ПОСТРОИТЬ вот этот конкретный элемент"
Контекстная изоляция: НЕ знает о системе в целом, только своё задание
```

### **1.2. ШЕСТЬ КРИТИЧЕСКИХ ДОКУМЕНТОВ (единый источник истины)**

Вся система работает на основе 6 неизменяемых документов:

1. **📄 ТЗ МОДУЛЯ 2** — Техническое задание на разрабатываемый модуль "Подбор удобрений по составу NPK"
2. **🗄️ NPK DATABASE v4.0** — Файл `npk-database.php` с методами `get_crops_list()`, `normalize_npk()` и другими
3. **🏗️ ЭТАЛОННАЯ АРХИТЕКТУРА** — Документ, описывающий взаимодействия классов, принципы "чёрных ящиков"
4. **⚠️ АРХИТЕКТУРНЫЕ ОГРАНИЧЕНИЯ** — Дополняющее ТЗ с явными запретами (что нельзя делать)
5. **🐛 СПИСОК ОШИБОК МОДУЛЯ 1** — История критических багов предыдущего модуля (URLSearchParams, стили в JS и др.)
6. **✅ ИНСТРУКЦИЯ ФИНАЛЬНОЙ ПРОВЕРКИ** — Чек-листы, тест-кейсы, критерии приёмки

**КРИТИЧЕСКОЕ ПРАВИЛО:** Эти 6 документов НЕ изменяются в процессе разработки. Любые изменения — только через остановку системы и обновление всех участников.

### **2.2. РАСПРЕДЕЛЕНИЕ ДОКУМЕНТОВ МЕЖДУ РОЛЯМИ**

Каждая роль получает ТОЛЬКО необходимый минимум:

```
АРХИТЕКТОР получает:
• ТЗ модуля 2
• Эталонная архитектура
НЕ получает: Ошибки модуля 1, Ограничения, Инструкции проверки

СТРАТЕГИЧЕСКИЙ АУДИТОР получает:
• Архитектурный план
• ТЗ модуля 2  
• Эталонная архитектура
• Контекст модулей (как интегрируется с существующим)
НЕ получает: Ошибки модуля 1, Технические ограничения

КООРДИНАТОР получает:
• Архитектурный план
• Список ошибок модуля 1
• Архитектурные ограничения
НЕ получает: ТЗ (полное), Эталонную архитектуру (полную)

ОПЕРАЦИОННЫЙ АУДИТОР получает:
• Готовый код для проверки
• Задание, по которому создавался код
• Список ошибок модуля 1 (только технические)
• Эталонная архитектура (только релевантные части)
НЕ получает: ТЗ, Стратегический контекст, Архитектурные решения

КОДЕР получает:
• ТОЛЬКО задание для текущего этапа
• Примеры кода (если есть в задании)
НЕ получает: Никаких других документов, контекста, истории
```

### **2.3. МЕХАНИЗМ КОНТЕКСТНОЙ ИЗОЛЯЦИИ**

**Принцип:** Каждая роль работает в информационном "пузыре", чтобы избежать когнитивной перегрузки и сохранить объективность.

**Как это работает на практике:**
- **Архитектор** не знает, что в модуле 1 были проблемы с AJAX через URLSearchParams
- **Кодер** не знает, почему задание требует использовать именно FormData()
- **Стратегический аудитор** не знает, что операционный аудитор отклонил код на предыдущем этапе
- **Операционный аудитор** не знает о стратегических решениях по архитектуре

**Выгоды:**
1. **Объективность проверок:** Аудиторы не подвержены групповому мышлению
2. **Фокус на задаче:** Каждый делает ТОЛЬКО свою часть
3. **Предотвращение наследования ошибок:** Ошибка в одном контексте не влияет на другие
4. **Масштабируемость:** Можно легко заменить любую роль

### **2.4. ТРИГГЕРНАЯ СИСТЕМА ДЛЯ АУДИТОРОВ**

Аудиторы вызываются НЕ на каждый этап, а по триггерам:

#### **КОГДА ВЫЗЫВАТЬ СТРАТЕГИЧЕСКОГО АУДИТОРА:**
```
✅ ВСЕГДА: При создании нового архитектурного плана
✅ ВСЕГДА: При финальной проверке всего модуля
✅ ЕСЛИ: Обнаружены противоречия между этапами
✅ ЕСЛИ: Изменения в ТЗ в процессе разработки (редкий случай)
❌ НЕ НАДО: Для проверки отдельных заданий или кода
```

#### **КОГДА ВЫЗЫВАТЬ ОПЕРАЦИОННОГО АУДИТОРА:**
```
✅ КРИТИЧЕСКИЕ КОМПОНЕНТЫ: Ядро системы, БД, безопасность
✅ СЛОЖНЫЕ ЗАДАНИЯ: Отмеченные Координатором как высокорисковые
✅ ИСТОРИЯ ОШИБОК: Если на предыдущих этапах были технические ошибки
✅ ПО ТРЕБОВАНИЮ: Если Координатор сомневается в своём решении
❌ НЕ НАДО: Для простых CSS/HTML, рутинных исправлений
```

**КРИТИЧЕСКИЙ ПРИМЕР:** Если задание предполагает работу с AJAX в WordPress — ВСЕГДА вызывать операционного аудитора, потому что в модуле 1 была критическая ошибка с URLSearchParams.

## **🔍 ЧАСТЬ 3: КРИТЕРИИ И ПРОВЕРКИ**

### **3.1. КРИТЕРИИ ДЛЯ СТРАТЕГИЧЕСКОГО АУДИТОРА**

Стратегический аудитор проверяет архитектурный план по 5 критериям:

**КРИТЕРИЙ 1: ПОЛНОТА ПОКРЫТИЯ ТЗ**
```
Проверка: Все ли требования из ТЗ отражены в плане?
Доказательство: Сопоставление каждого пункта ТЗ с элементом плана
Пример ошибки: В ТЗ требуется "Instant Preview", а в плане нет JavaScript файла для предпросмотра
```

**КРИТЕРИЙ 2: АРХИТЕКТУРНАЯ ЦЕЛОСТНОСТЬ**
```
Проверка: Соответствует ли план эталонной архитектуре?
Доказательство: Сравнение структур, принципов, взаимодействий
Пример ошибки: План предполагает, что Data_Adapter вызывает Calculation_Engine (нарушение эталонной архитектуры)
```

**КРИТЕРИЙ 3: РЕАЛИЗУЕМОСТЬ**
```
Проверка: Можно ли технически реализовать этот план?
Доказательство: Проверка зависимостей, доступности методов БД
Пример ошибки: План использует метод NPK_Database::get_new_method(), которого нет в v4.0
```

**КРИТЕРИЙ 4: ИНТЕГРАЦИОННАЯ СОВМЕСТИМОСТЬ**
```
Проверка: Будет ли новый модуль работать с существующей системой?
Доказательство: Анализ точек интеграции, общих ресурсов
Пример ошибки: Новый модуль пытается перезаписать файлы модуля 1
```

**КРИТЕРИЙ 5: МАСШТАБИРУЕМОСТЬ**
```
Проверка: Позволяет ли план развивать систему в будущем?
Доказательство: Анализ структуры на предмет "закрытости для изменений"
Пример ошибки: Жёсткая привязка к конкретной версии БД без возможности обновления
```

### **3.2. КРИТЕРИИ ДЛЯ КООРДИНАТОРА (проверка качества)**

Координатор проверяет выполненное задание по чек-листу:

**БАЗОВЫЙ ЧЕК-ЛИСТ ДЛЯ ЛЮБОГО ЗАДАНИЯ:**
```
[ ] Все пункты задания выполнены
[ ] Имена файлов в kebab-case (npk-calculators.php, не npkCalculators.php)
[ ] CSS селекторы с префиксом .npk-
[ ] Data-атрибуты с префиксом data-npk-
[ ] Нет статических стилей в JS/HTML (только в CSS файле)
[ ] Используются правильные методы БД (v4.0)
[ ] AJAX использует FormData() (НЕ URLSearchParams, НЕ JSON)
[ ] UI обновления в requestAnimationFrame()
[ ] Нет нарушений из списка ошибок модуля 1
[ ] Код проходит базовые тесты (синтаксис, запуск)
```

**ЧЕК-ЛИСТ ДЛЯ КОНКРЕТНЫХ ТИПОВ ЗАДАНИЙ:**

**Для PHP классов:**
```
[ ] Использует только NPK_Database:: методы (0 прямых SQL)
[ ] Соблюдает принципы эталонной архитектуры
[ ] Имеет type hints для методов
[ ] Обрабатывает edge cases (нулевые значения, отсутствие данных)
```

**Для JavaScript:**
```
[ ] Instant preview работает мгновенно (<100мс)
[ ] Предзагрузка данных выполнена
[ ] Нет дублирования бизнес-логики (алгоритмы только в PHP)
[ ] Корректная обработка ошибок AJAX
```

**Для CSS:**
```
[ ] Все статические стили ТОЛЬКО в CSS файле
[ ] Селекторы с префиксом .npk-
[ ] Адаптивная вёрстка (медиа-запросы)
[ ] Нет !important (кроме крайней необходимости)
```

### **3.3. КРИТЕРИИ ДЛЯ ОПЕРАЦИОННОГО АУДИТОРА**

Операционный аудитор проверяет техническую корректность:

**КРИТЕРИЙ 1: СИНТАКСИЧЕСКАЯ КОРРЕКТНОСТЬ**
```
Проверка: Корректный ли синтаксис PHP/JS?
Доказательство: Запуск через php -l, проверка в консоли браузера
```

**КРИТЕРИЙ 2: СООТВЕТСТВИЕ ЗАДАНИЮ**
```
Проверка: Делает ли код именно то, что требовалось?
Доказательство: Сопоставление кода с пунктами задания
```

**КРИТЕРИЙ 3: WORDPRESS СТАНДАРТЫ**
```
Проверка: Соблюдает ли WordPress coding standards?
Доказательство: Проверка именования функций, хуков, безопасности
```

**КРИТЕРИЙ 4: БЕЗОПАСНОСТЬ**
```
Проверка: Нет ли уязвимостей (XSS, SQL injection, CSRF)?
Доказательство: Проверка экранирования, nonce, prepared statements
```

**КРИТЕРИЙ 5: ФУНКЦИОНАЛЬНАЯ КОРРЕКТНОСТЬ**
```
Проверка: Работает ли код как задумано?
Доказательство: Тестовый запуск, проверка возвращаемых значений
```

### **3.4. КРИТЕРИИ ДЛЯ АРХИТЕКТОРА (проверка архитектурного соответствия)**

Архитектор проверяет, что созданный код соответствует архитектурному плану:

**КРИТЕРИЙ 1: СООТВЕТСТВИЕ СТРУКТУРЕ**
```
Проверка: Находятся ли файлы в правильных папках?
Доказательство: Сравнение фактической структуры с планом
```

**КРИТЕРИЙ 2: СОБЛЮДЕНИЕ ЗАВИСИМОСТЕЙ**
```
Проверка: Созданы ли все зависимости перед использованием?
Доказательство: Проверка require_once, вызовов методов
```

**КРИТЕРИЙ 3: ИНТЕГРАЦИЯ С СУЩЕСТВУЮЩЕЙ СИСТЕМОЙ**
```
Проверка: Не ломает ли новый код существующий функционал?
Доказательство: Тестовая установка, проверка работы модуля 1
```

**КРИТЕРИЙ 4: ИСПОЛЬЗОВАНИЕ БД v4.0**
```
Проверка: Используются ли новые методы БД?
Доказательство: Поиск устаревших вызовов, проверка normalize_npk()
```

## **🚀 ЧАСТЬ 4: УПРАВЛЕНИЕ И РАЗРЕШЕНИЕ ПРОБЛЕМ**

### **4.1. ТИПОВЫЕ ПРОБЛЕМЫ И ИХ РЕШЕНИЯ**

#### **ПРОБЛЕМА: АРХИТЕКТОР СОЗДАЛ НЕПОЛНЫЙ ПЛАН**
```
Симптомы: В плане отсутствуют критически важные компоненты
Решение: Стратегический аудитор возвращает план с указанием недостатков
Действия: Архитектор дополняет план → повторная проверка
```

#### **ПРОБЛЕМА: КОДЕР ВЫПОЛНИЛ ЗАДАНИЕ НЕПРАВИЛЬНО**
```
Симптомы: Код не соответствует пунктам задания
Решение: Координатор возвращает задание с указанием ошибок
Действия: Кодер исправляет → повторная проверка Координатором
ВАЖНО: Координатор НЕ объясняет "почему так", только "что неправильно"
```

#### **ПРОБЛЕМА: ОПЕРАЦИОННЫЙ АУДИТОР ОТКЛОНИЛ КОД, А КООРДИНАТОР ОДОБРИЛ**
```
Симптомы: Противоречивые решения разных ролей
Решение: Master-архитектор анализирует конфликт
Действия: 
1. Если аудитор прав → Координатор исправляет свой чек-лист
2. Если аудитор не прав → уточняются критерии проверки
3. Код возвращается на доработку с учётом решения
```

#### **ПРОБЛЕМА: ОБНАРУЖЕНА ОШИБКА В ТЗ В ПРОЦЕССЕ РАЗРАБОТКИ**
```
Симптомы: Требования противоречивы или нереализуемы
Решение: ОСТАНОВКА всей разработки
Действия:
1. Master-архитектор фиксирует проблему
2. Заказчик вносит изменения в ТЗ
3. ВСЕ документы обновляются
4. Разработка начинается заново с шага 1
```

#### **ПРОБЛЕМА: МЕДЛЕННАЯ РАЗРАБОТКА ИЗ-ЗА МНОЖЕСТВА ПРОВЕРОК**
```
Симптомы: Каждый этап занимает слишком много времени
Решение: Оптимизация триггеров для аудиторов
Действия:
1. Упростить чек-листы Координатора
2. Вызывать операционного аудитора только для критических компонентов
3. Упростить задания для кодера (меньше пунктов)
```

### **4.2. ПРАВИЛА ЭСКАЛАЦИИ ПРОБЛЕМ**

Каждая роль эскалирует проблемы ТОЛЬКО вверх по иерархии:

```
КОДЕР → может эскалировать только к КООРДИНАТОРУ
  Вопросы: "Не понимаю пункт задания", "Техническая неясность"
  
КООРДИНАТОР → может эскалировать к MASTER-АРХИТЕКТОРУ
  Вопросы: "Конфликт критериев", "Ошибка в документе", "Не могу принять решение"

АУДИТОРЫ → могут эскалировать только к MASTER-АРХИТЕКТОРУ
  Вопросы: "Неполный пакет для проверки", "Противоречивые требования"

АРХИТЕКТОР → может эскалировать к MASTER-АРХИТЕКТОРУ
  Вопросы: "Требования ТЗ нереализуемы", "Конфликт с существующей архитектурой"
```

**ЗАПРЕЩЕНО:**
- Кодер обращается напрямую к Архитектору
- Аудиторы общаются между собой
- Координатор изменяет ТЗ или архитектурные документы

### **4.3. МЕХАНИЗМ ОБНОВЛЕНИЯ СИСТЕМЫ**

```
ШАГ 1: ФИКСАЦИЯ ПРОБЛЕМЫ

ШАГ 2: ОБНОВЛЕНИЕ ДОКУМЕНТОВ

ШАГ 3: ОБНОВЛЕНИЕ РОЛЕЙ

• Уведомить всех о изменениях
• При необходимости перезапустить текущий этап

ШАГ 4: ПРЕВЕНТИВНЫЕ МЕРЫ
```
