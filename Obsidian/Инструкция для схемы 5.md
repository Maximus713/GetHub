# 📋 **ПОШАГОВАЯ ИНСТРУКЦИЯ ДЛЯ СХЕМЫ ВЗАИМОДЕЙСТВИЯ ЧАТОВ**

## **ШАГ 1: ИНИЦИАЛИЗАЦИЯ (ЗАКАЗЧИК)**

### **1.1. Подготовка документов:**
```
ЗАКАЗЧИК подготавливает 6 документов:
1. ТЗ модуля 2
2. БД версии 4.0
3. Эталонная архитектура
4. Список ошибок модуля 1
5. Ограничения
6. Инструкция проверки
```

### **1.2. Создание чатов:**
```
Создать 3 отдельных чата:
- ЧАТ 1: АРХИТЕКТОР (назвать "Архитектор модуля 2")
- ЧАТ 2: КООРДИНАТОР (назвать "Координатор модуля 2")
- ЧАТ 3: КОДЕР (назвать "Кодер модуля 2")
```

---

## **ШАГ 2: РАЗДЕЛЕНИЕ ДОКУМЕНТОВ**

### **2.1. В ЧАТ 1 (АРХИТЕКТОР):**
```
Отправить только:
✅ ТЗ модуля 2 (полностью)
✅ Эталонная архитектура

НЕ отправлять:
❌ Список ошибок модуля 1
❌ Ограничения
❌ Инструкция проверки
❌ БД (только ссылка, что существует версия 4.0)
```

### **2.2. В ЧАТ 2 (КООРДИНАТОР):**
```
Отправить:
✅ Архитектурный план (после получения от Архитектора)
✅ Список ошибок модуля 1
✅ Ограничения
✅ Инструкция проверки
```

### **2.3. В ЧАТ 3 (КОДЕР):**
```
Отправить ТОЛЬКО когда нужно:
✅ Конкретное задание (после получения от Координатора)
✅ Чек-лист для этого задания
```

---

## **ШАГ 3: РАБОТА АРХИТЕКТОРА (ЧАТ 1)**

### **3.1. Получить команду от Заказчика:**
```
Заказчик → Чат 1: "Создай архитектурный план для модуля 2"
```

### **3.2. Выполнить функции Архитектора:**
```
1. Проанализировать ТЗ на архитектурном уровне
2. Создать структуру папок (дерево файлов)
3. Определить порядок создания файлов
4. Выявить критические зависимости
5. Разделить на этапы разработки
```

### **3.3. Создать выходной документ:**
```
Название: "АРХИТЕКТУРНЫЙ ПЛАН МОДУЛЯ 2"
Содержание:
- Полное дерево файлов
- Порядок создания (этапы 1-6)
- Критические зависимости
- Контрольные точки
```

### **3.4. Передать результат:**
```
Архитектор → Заказчик: "Архитектурный план готов"
Заказчик → Координатор: Пересылает архитектурный план
```

---

## **ШАГ 4: РАБОТА КООРДИНАТОРА (ЧАТ 2)**

### **4.1. Получить данные:**
```
Получить от Заказчика:
1. Архитектурный план
2. Список ошибок модуля 1
3. Ограничения
4. Инструкция проверки
```

### **4.2. Создать задания для кодера:**
```
Для каждого этапа из архитектурного плана:
1. Разбить на конкретные задания
2. Создать чек-лист проверки
3. Учесть ошибки модуля 1 в формулировках
4. Добавить явные запреты
```

### **4.3. Пример задания:**
```markdown
## ЗАДАНИЕ №1: КАРКАС МОДУЛЯ

### ЦЕЛЬ: Создать основной файл модуля

### ФАЙЛ: module-fertilizer-selector/fertilizer-selector-module.php

### ЧТО СДЕЛАТЬ:
1. Создать файл с точным именем
2. Реализовать регистрацию модуля (аналогично модулю 1)
3. Подключить хуки жизненного цикла WordPress
4. Зарегистрировать шорткод [npk_fertilizer_selector]

### ЧЕК-ЛИСТ ПРОВЕРКИ:
[ ] Файл создан в правильной папке
[ ] Использует NPK_Calculators_Core::register_module()
[ ] Регистрирует шорткод на раннем init
[ ] Подключает зависимости в правильном порядке

### ЗАПРЕТЫ:
❌ Не изменять файлы модуля 1
❌ Не использовать старые методы БД
```

### **4.4. Передать задание:**
```
Координатор → Заказчик: "Задание №1 готово"
Заказчик → Кодер: Пересылает задание №1
```

---

## **ШАГ 5: РАБОТА КОДЕРА (ЧАТ 3)**

### **5.1. Получить задание:**
```
Получить от Заказчика:
- Конкретное задание (например, "Задание №1")
- Только для текущего этапа
```

### **5.2. Выполнить задание:**
```
1. Прочитать инструкцию полностью
2. Создать указанный файл
3. Реализовать указанные методы
4. Пройти самопроверку по чек-листу
5. Добавить дебаг-заголовок
```

### **5.3. Пример выполнения:**
```php
<?php
// ============================================
// ДЕБАГ-ПРОВЕРКИ: fertilizer-selector-module.php
// ============================================
// Задание №1 выполнено:
// [x] Файл в правильной папке
// [x] Регистрация модуля через Core
// [x] Шорткод зарегистрирован
// ============================================

// Код строго по заданию...
```

### **5.4. Отправить результат:**
```
Кодер → Заказчик: "Задание №1 выполнено + код"
Заказчик → Координатор: Пересылает код
```

---

## **ШАГ 6: ПРОВЕРКА КАЧЕСТВА (КООРДИНАТОР)**

### **6.1. Получить код от Кодера:**
```
Получить через Заказчика готовый код
```

### **6.2. Проверить по чек-листу:**
```
Для каждого пункта чек-листа:
✅ - выполнено
❌ - не выполнено
⚠️ - частично выполнено
```

### **6.3. Принять решение:**
```
Если ВСЕ пункты ✅:
Координатор → Заказчик: "Задание №1 прошло проверку качества"

Если есть ❌:
Координатор → Заказчик: "Задание №1 не прошло, ошибки: [список]"
Заказчик → Кодер: "Исправь ошибки [список]"
Повторить шаг 5
```

---

## **ШАГ 7: ПРОВЕРКА АРХИТЕКТУРЫ (АРХИТЕКТОР)**

### **7.1. Получить проверенный код:**
```
Заказчик → Архитектор: "Код задания №1 прошел проверку качества"
```

### **7.2. Проверить архитектуру:**
```
Проверить:
1. Соответствует ли структуре из плана?
2. Правильные ли зависимости?
3. Нарушены ли архитектурные принципы?
4. Интегрируется ли с существующей системой?
```

### **7.3. Принять решение:**
```
Если архитектура корректна:
Архитектор → Заказчик: "Архитектура задания №1 корректна"

Если есть нарушения:
Архитектор → Заказчик: "Архитектурные нарушения: [список]"
Заказчик → Координатор → Кодер: "Исправь архитектурные нарушения"
```

---

## **ШАГ 8: ЦИКЛ РАЗРАБОТКИ**

### **8.1. Для каждого этапа:**
```
ПОВТОРИТЬ шаги 4-7:
1. Координатор создаёт задание для этапа
2. Кодер выполняет задание
3. Координатор проверяет качество
4. Архитектор проверяет архитектуру
```

### **8.2. Этапы модуля 2:**
```
Этап 1: Каркас модуля
Этап 2: Selection Engine (ядро логики)
Этап 3: Data Adapter
Этап 4: AJAX Handler
Этап 5: Shortcode + Template
Этап 6: JavaScript + CSS
Этап 7: Интеграция и тестирование
```

---

## **ШАГ 9: ИНТЕГРАЦИЯ И ТЕСТИРОВАНИЕ**

### **9.1. После всех этапов:**
```
Координатор собирает все файлы
Проводит интеграционное тестирование
```

### **9.2. Финальная проверка:**
```
Архитектор проверяет весь модуль целиком
Координатор проверяет все чек-листы
```

### **9.3. Сдача проекта:**
```
Архитектор → Заказчик: "Модуль 2 архитектурно корректный"
Координатор → Заказчик: "Модуль 2 прошел все проверки качества"
Заказчик получает готовый модуль
```

```
Архитектор ↔ Кодер: НЕТ ПРЯМОГО ОБЩЕНИЯ
Все общение только через Заказчика
```

### **Правило 2: Один источник истины**
```
БД: только версия 4.0 из npk-database.php
Архитектура: только из эталонного документа
```

### **Правило 3: Последовательность проверок**
```
1. Кодер → самопроверка
2. Координатор → проверка качества
3. Архитектор → проверка архитектуры
НЕЛЬЗЯ пропускать этапы!
```

### **Правило 4: Изоляция контекста**
```
Каждый чат получает только необходимое
Нельзя "улучшать" то, что не в твоей зоне
```

## **📊 КОНТРОЛЬНЫЕ ТОЧКИ ДЛЯ ЗАКАЗЧИКА:**

### **После каждого этапа проверять:**
```
✅ Задание создано Координатором
✅ Код выполнен Кодером
✅ Качество проверено Координатором
✅ Архитектура проверена Архитектором
```

### **Документы для отслеживания:**
```
1. Архитектурный план (от Архитектора)
2. Задания по этапам (от Координатора)
3. Чек-листы проверок (от Координатора)
4. Отчёты о проверках (от обоих)
```

## **⚡ ЭКСТРЕННЫЕ СИТУАЦИИ:**

### **Если Кодер не понимает задание:**
```
Кодер → Заказчик: "Уточнение по заданию №X"
Заказчик → Координатор: "Уточни задание №X"
Координатор → уточняет → Заказчик → Кодер
```

### **Если обнаружена ошибка в ТЗ:**
```
Любой чат → Заказчик: "Обнаружена проблема в ТЗ"
Заказчик принимает решение
Обновляет ТЗ для всех чатов
```

### **Если нужны изменения в архитектуре:**
```
ТОЛЬКО Заказчик может инициировать
Архитектор вносит изменения в план
Уведомляются все чаты
```
