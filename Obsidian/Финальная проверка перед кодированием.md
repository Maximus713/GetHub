# 🚀 **ИНСТРУКЦИЯ ФИНАЛЬНОЙ ПРОВЕРКИ ПЕРЕД КОДИРОВАНИЕМ**

## **⚡ НЕМЕДЛЕННО ПЕРЕД НАЧАЛОМ КОДИРОВАНИЯ:**

### **ШАГ 0: ПАУЗА И ОСОЗНАНИЕ**

"СТОП. Сейчас я буду писать код. 
Я знаю ВСЕ требования из ТЗ.
Я понял ВСЕ архитектурные ограничения.
Я осознаю ВСЕ типовые ошибки.
Теперь я действую по чёткому плану."


### **ШАГ 1: ВОСПРОИЗВЕДЕНИЕ СТРУКТУРЫ**
**Не начинать кодить, пока не выполнено:**
1. ✅ Мысленно воспроизвести ВСЮ структуру папок из ТЗ
2. ✅ Увидеть в голове КАЖДЫЙ файл и его назначение
3. ✅ Понимать ВСЕ связи между файлами
4. ✅ Знать, какие данные куда передаются

### **ШАГ 2: АРХИТЕКТУРНЫЙ КОНТРОЛЬ (на каждый файл)**
**Перед созданием ЛЮБОГО файла спросить:**


"ЭТОТ ФАЙЛ:
1. Какую РОЛЬ играет в архитектуре? (ТЗ п.3.2)
2. Кого МОЖЕТ вызывать? (Таблица из Эталонной архитектуры)
3. Кого НЕ МОЖЕТ вызывать? (Жёсткие ограничения)
4. Какие ДАННЫЕ получает/возвращает?
5. При переходе к кодированию очередного файла обязательно возвращаться к ТЗ и заново прочитывать (но не выводить на печать) все данные, относящиеся именно к этому файлу.
6. Проверять, есть ли для этого файла ТОЧНЫЕ ТРЕБОВАНИЯ в ТЗ?"


### **ШАГ 3: АНТИ-ОШИБОЧНЫЕ ВОПРОСЫ (перед каждой функцией)**
**Перед написанием КАЖДОЙ функции!**


"ЭТА ФУНКЦИЯ:
1. Не дублирует ли логику из другого файла? (Запрет дублирования)
2. Определяет ли state? (Только Calculation_Engine!)
3. Содержит ли бизнес-логику в UI? (Запрещено)
4. Может ли вызвать моргание UI? (Дебаунс, requestAnimationFrame)
5. Использует ли правильный источник данных? (Только npk-database.php)"


### **ШАГ 4: СЦЕНАРНЫЕ ПРОВЕРКИ (во время кодирования)**
**При написании кода постоянно представлять:**


"А ТАК ЛИ ЭТО РАБОТАЕТ В РЕАЛЬНОСТИ?
1. Пользователь нажимает кнопку грунта → цвет меняется СИНХРОННО везде
2. Пользователь тянет слайдер → нет морганий, дебаунс 500мс
3. Пользователь вводит 0,04% → корректируется до 0,05%
4. Нет интернета → калькулятор РАБОТАЕТ на локальных расчётах
5. Быстрый ввод → предыдущие AJAX-запросы ОТМЕНЯЮТСЯ"


### **ШАГ 5: ТОЧКИ ВАЛИДАЦИИ (контрольные точки)**
**После каждого логического блока останавливаться и проверять:**


"КОНТРОЛЬНАЯ ТОЧКА:
1. Соответствует ли ТОЧНО ТЗ? (цитата из пункта)
2. Не нарушает ли архитектуру? (ссылка на ограничение)
3. Не повторяет ли известную ошибку? (из файла "Ошибки")
4. Можно ли сделать ПРОЩЕ? (правило минимального изменения)
5. Будет ли понятно другому разработчику?"


## **🎯 КЛЮЧЕВЫЕ ПРИНЦИПЫ НА ВСЁ ВРЕМЯ РАБОТЫ:**

### **ПРИНЦИП 1: "ОДИН ФАЙЛ — ОДНА ЗАВЕРШЁННАЯ РАБОТА"**

1. Берём ОДИН файл (по приоритету из ТЗ)
2. Возвращаемся к ТЗ → читаем ВСЕ требования к этому файлу
3. Создаём файл ПОЛНОСТЬЮ готовым (от первой до последней строки)
4. Выводим файл НЕМЕДЛЕННО после создания
5. Только потом переходим к следующему файлу
6. При переходе к новому файлу — снова возвращаемся к ТЗ

### **ПРИНЦИП 2: "ОДНА РОЛЬ — ОДИН ФАЙЛ"**

Calculation_Engine = ТОЛЬКО формулы
AJAX_Handler = ТОЛЬКО транспорт
Data_Adapter = ТОЛЬКО подготовка данных
Shortcode = ТОЛЬКО HTML
JavaScript = ТОЛЬКО UI-логика


### **ПРИНЦИП 3: "DATA FLOW СВЕРХУ ВНИЗ"**
```
npk-database.php → Calculation_Engine → AJAX_Handler → JavaScript
          ↓
      Data_Adapter → JavaScript
```

### **ПРИНЦИП 4: "STATE — ТОЛЬКО В ЯДРЕ"**
```
"STATE определяется ТОЛЬКО в Calculation_Engine.
JavaScript может ТОЛЬКО предварительно определять для UX.
Data_Adapter НИКОГДА не определяет state."
```

### **ПРИНЦИП 5: "UI НЕ ЗНАЕТ ФОРМУЛ"**
```
"JavaScript знает ТОЛЬКО:
- Как отобразить данные
- Как обработать пользовательский ввод
- Как отправить запрос на сервер
НО НИКОГДА не содержит бизнес-логику"
```

## **🔧 ТЕХНИЧЕСКИЕ ПРАВИЛА (жёсткие):**

### **ДЛЯ PHP:**
```
1. Все классы — синглтоны (кроме Calculation_Engine)
2. Все публичные методы имеют type hints
3. Все исключения обрабатываются
4. Все данные валидируются на входе
5. WordPress хуки регистрируются корректно
```

### **ДЛЯ JavaScript:**
```
1. Используется requestAnimationFrame для анимаций
2. Все AJAX-запросы имеют дебаунс
3. Все запросы можно отменить (AbortController)
4. При ошибках — fallback на локальные расчёты
5. Цвета обновляются СИНХРОННО
```

### **ДЛЯ CSS:**
```
1. Без внешних фреймворков
2. Все селекторы с префиксом .npk-
3. Цветовая логика из ТЗ п.6.4
4. Адаптивность для мобильных
5. Плавные переходы
```

Обязательно для выполнения!
- перед созданием каждого файла обязательно обращаться к ТЗ, находить все требования ТЗ к содержимому создаваемого файла и обновлять в своей памяти эти требования.
- Переходить к созданию очередного файла только после процедуры обновления данных именно для создаваемого файла.
- Непосредственно перед выводом содержимого файла на печать, сначала создавать текст: "Файл создан после обращения к Техническому Заданию. Все требования ТЗ в файле соблюдены!"  И только после этой фразы выводить содержание файла. Отсутствие этой фразы будет означать. что файл создан без обновления информации из ТЗ с высокой вероятностью создания ошибок.
- После создания КАЖДОГО  файла обязательно прочитывать ВЕСЬ этот текст (**ИНСТРУКЦИЯ ФИНАЛЬНОЙ ПРОВЕРКИ ПЕРЕД КОДИРОВАНИЕМ**) и выводить на печать текст: "Инструкцию финальной проверки повторил!" После создания последнего файла плагина  эту операцию не делать.

- Начинать работу над новым файлом без обращения к ТЗ и обновления в памяти требований к создаваемому файлу.
- Пропускать прочтение этой инструкции после создания очередного файла.
