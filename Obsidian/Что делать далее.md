**После создания ТЗ — следующие КРИТИЧЕСКИЕ действия:**

## **ЭТАП 1: ПРОВЕРКА И СОГЛАСОВАНИЕ (сейчас)**

### **1.1. Проверить ТЗ на внутренние противоречия:**
- [ ] **Архитектурные:** "Создайте папку" vs "Папка уже существует"
- [ ] **Технические:** Алгоритмы, формулы, пороги
- [ ] **Интеграционные:** Совместимость с первым модулем
- [ ] **Бизнес-логика:** Соответствует ли задачам пользователя?

### **1.2. Проверить совместимость с существующим плагином:**
```javascript
// Критические проверки
const existingPlugin = {
  structure: ['npk-calculators.php', 'shared/config/', 'module-concentration/'],
  db: 'npk-database.php (с priority/additives)',
  architecture: 'слоистая (БД → логика → представление)',
  techStack: 'WordPress, чистый PHP/JS, FormData AJAX'
};

const newTZ = {
  usesSameDB: true,        // ДА
  sameArchitecture: true,  // ДА  
  noConflicts: true,       // ДА
  independentModule: true  // ДА
};
```

### **1.3. Утвердить ТЗ с заинтересованными сторонами:**
- **Product Owner:** Соответствует ли бизнес-задачам?
- **Технический лид:** Реализуемо ли технически?
- **Разработчик 1-го модуля:** Не нарушит ли существующий функционал?
- **Тестировщик:** Можно ли будет протестировать?

## **ЭТАП 2: ПОДГОТОВКА К РАЗРАБОТКЕ**

### **2.1. Создать репозиторий/ветку:**
```
npk-calculators/
├── main/                 ← Существующий плагин (module-concentration)
└── feature/fertilizer-selector/ ← Новая ветка для разработки
```

### **2.2. Подготовить среду разработки:**
- WordPress-среда с установленным плагином `npk-calculators`
- Доступ к существующей БД `npk-database.php`
- Тестовые данные для проверки подбора

### **2.3. Создать чек-лист реализации:**
```markdown
## ЧЕК-ЛИСТ РАЗРАБОТКИ МОДУЛЯ

### Фаза 1: Каркас модуля (1 день)
- [ ] Создать папку `module-fertilizer-selector/`
- [ ] Реализовать автозагрузку в существующий плагин
- [ ] Зарегистрировать шорткод `[npk_fertilizer_selector]`
- [ ] Подключить общую БД `NPK_Database::`

### Фаза 2: Ядро логики (2 дня)
- [ ] Класс `Selection_Engine` с алгоритмом Отиаи
- [ ] Учёт полей `priority` и `additives`
- [ ] AJAX-обработчик `npk_fertilizer_select`
- [ ] Генерация подсказок

### Фаза 3: Интерфейс (2 дня)
- [ ] HTML-шаблон таблицы
- [ ] JavaScript для мгновенного пересчёта
- [ ] Прогресс-бары с цветовой индикацией
- [ ] Адаптивность под мобильные

### Фаза 4: Интеграция и тестирование (1 день)
- [ ] Проверить работу обоих шорткодов
- [ ] Убедиться в отсутствии конфликтов
- [ ] Протестировать производительность
- [ ] Документировать API модуля
```

## **ЭТАП 3: РАЗРАБОТКА И КОНТРОЛЬ КАЧЕСТВА**

### **3.1. Code Review с акцентом на совместимость:**
```php
// КРИТИЧЕСКИЕ МОМЕНТЫ ДЛЯ REVIEW:
// 1. Не создаёт ли дубли плагина?
// 2. Не изменяет ли общую БД?
// 3. Уникальны ли имена классов/функций?
// 4. Корректна ли автозагрузка?
```

### **3.2. Тестирование совместимости:**
```javascript
// ТЕСТЫ ДЛЯ ПРОВЕРКИ:
test('Оба модуля работают одновременно', () => {
  expect(shortcodeExists('[npk_concentration]')).toBe(true);
  expect(shortcodeExists('[npk_fertilizer_selector]')).toBe(true);
  expect(noConflictsBetweenModules()).toBe(true);
});

test('Общая БД не изменена', () => {
  expect(databaseIntegrity()).toBe(true);
  expect(noNewTablesCreated()).toBe(true);
});
```

### **3.3. Документирование:**
- **README.md** для модуля (инструкция установки/использования)
- **API documentation** (хуки, фильтры, шорткоды)
- **Changelog** (что добавлено, изменено, исправлено)

## **ЭТАП 4: ВНЕДРЕНИЕ И ПОДДЕРЖКА**

### **4.1. План развёртывания:**
1. **Dev-среда:** Тестирование модуля отдельно
2. **Staging:** Тестирование совместно с первым модулем
3. **Production:** Поэтапный rollout с мониторингом

### **4.2. Мониторинг после внедрения:**
```yaml
Метрики для отслеживания:
- Производительность: время ответа < 0.5с
- Совместимость: оба шорткода работают
- Ошибки: отсутствие конфликтов в логах
- Использование: статистика вызовов каждого модуля
```

### **4.3. Подготовка к третьему модулю:**
- **Выделить общие компоненты** в `shared/` (если нужно)
- **Документировать архитектурные решения**
- **Создать шаблон** для будущих модулей

## **КРИТИЧЕСКИЕ РИСКИ И ИХ МИТИГАЦИЯ**

| Риск | Вероятность | Влияние | Меры предотвращения |
|------|------------|---------|---------------------|
| **Конфликт имён** | Высокая | Критическое | Уникальные префиксы, code review |
| **Нарушение работы 1-го модуля** | Средняя | Критическое | Изоляция модулей, тестирование совместимости |
| **Ошибки в алгоритме подбора** | Высокая | Высокое | Юнит-тесты, проверка агрономом |
| **Проблемы с производительностью** | Низкая | Среднее | Оптимизация запросов, кэширование |

2. **Подготовить** тестовые данные
3. **Настроить** систему контроля версий
