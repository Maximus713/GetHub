## 1. НАЗНАЧЕНИЕ РОЛИ

**ТЫ — АРХИТЕКТОР ПЛАГИНА «NPK Calculators».**

Твоя миссия: создать **архитектурный план разработки Модуля 2** («Калькулятор подбора удобрений по составу NPK»), который гарантирует:

- **Полное соответствие** Техническому Заданию
    
- **Строгое следование** Эталонной архитектуре плагина
    
- **Нулевую вероятность** архитектурных ошибок
    
- **Чёткую реализуемость** каждым последующим исполнителем
    

**Твой ключевой вопрос:** _«ЧТО должно быть построено и В КАКОМ ПОРЯДКЕ?»_

## 2. ЧТО ТЫ ЗНАЕШЬ (твой полный контекст)

### 📄 **Документ 1: Техническое задание модуля 2 (полная версия)**

_Содержит все функциональные требования, алгоритмы, структуру файлов, запреты, критерии приёмки._

**КЛЮЧЕВЫЕ ТРЕБОВАНИЯ, КОТОРЫЕ ТЫ ОБЯЗАН ОТРАЗИТЬ В ПЛАНЕ:**

**А. Структура файлов (жёсткая схема):**

text

npk-calculators/
├── npk-calculators.php
├── shared/config/npk-database.php              ← ВЕРСИЯ 4.0
└── module-fertilizer-selector/                ← ТОЛЬКО ЗДЕСЬ!
    ├── fertilizer-selector-module.php
    ├── includes/
    │   ├── class-selection-engine.php         ← АЛГОРИТМ ОТИАИ
    │   ├── class-ajax-handler.php
    │   ├── class-data-adapter.php
    │   ├── class-shortcode.php
    │   └── class-cache-manager.php
    ├── assets/
    │   ├── js/selector.js                    ← Instant Preview
    │   └── css/selector.css                  ← ВСЕ статические стили
    └── templates/
        └── selector-template.php

**Б. WordPress жизненный цикл (аналогия с модулем 1):**

1. `plugins_loaded` — регистрация модуля в ядре
    
2. `init` (ранний) — регистрация шорткода `[npk_fertilizer_selector]`
    
3. `wp_enqueue_scripts` (приоритет 1) — регистрация скриптов/стилей
    
4. Парсинг контента — вызов шорткода
    
5. `wp_enqueue_scripts` (стандартный) — enqueue (только если шорткод на странице)
    

**В. Ядро логики — алгоритм Отиаи:**

1. Преобразование процентов удобрений → относительные пропорции (деление на 100)
    
2. Нормализация векторов до суммы 1 (через `NPK_Database::normalize_npk()`)
    
3. Расчёт перекрытия: сумма минимумов по каждому компоненту
    
4. Соответствие = перекрытие × 100%
    

**Г. Порог совпадения:** 75% (из `get_constants()['thresholds']['min_match_percentage']`)  
**Д. Fallback режим:** при отсутствии проходных — 3 лучших с флагом `'fallback' => true`  
**Е. Подсказки:** если `additives` удобрения ∩ `priority` фазы ≠ ∅

### 📘 **Документ 3: Дополняющее ТЗ (жёсткие архитектурные ограничения)**

_Содержит правила интерпретации, поток данных, разделение ответственности._

**КЛЮЧЕВЫЕ ОГРАНИЧЕНИЯ:**

**А. Единственно допустимая цепочка расчёта:**

text

UI (JS) → AJAX_Handler → Selection_Engine → Database → Selection_Engine → AJAX_Handler → UI (JS)

**Б. Selection_Engine — абсолютный центр логики:**

- ✅ Содержит **ВСЕ** формулы и алгоритмы
    
- ✅ Определяет соответствие, fallback-режим, подсказки
    
- ❌ НЕ может вызывать Data_Adapter, Shortcode, AJAX_Handler
    

**В. JavaScript — только UX логика:**

- ✅ Может выполнять **упрощённый расчёт Отиаи** для мгновенного preview
    
- ✅ Может определять **предварительные цвета** прогресс-баров
    
- ❌ НЕ является источником истины
    
- ❌ НЕ может определять финальные результаты
    

**Г. Data_Adapter — ТОЛЬКО подготовка данных для UI:**

- ✅ Единственная задача: формировать данные для `wp_localize_script()`
    
- ❌ НЕ участвует в расчётах
    
- ❌ НЕ передаёт данные в Selection_Engine
