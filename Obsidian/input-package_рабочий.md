2. ПОРЯДОК СОЗДАНИЯ КОМПОНЕНТОВ
   3. [fertilizer-selector-module.php] → Фундамент жизненного цикла. Без регистрации модуля остальные файлы не будут загружены WordPress.
   4. [class-selection-engine.php] → Ядро логики. Все остальные PHP-компоненты зависят от его API; должен существовать до их написания.
   5. [class-data-adapter.php] → Подготовка данных для JS. Требует Selection_Engine для типовой валидации (но НЕ расчётов) и БД для извлечения справочников.
   6. [class-cache-manager.php] → Оптимизация. Зависит от Selection_Engine, который кеширует; Data_Adapter использует кеш для предзагрузки.
   7. [class-ajax-handler.php] → Транспортный слой. Зависит от Selection_Engine и Cache_Manager; должен быть готов до написания JS.
   8. [class-shortcode.php] → Интеграция с темой. Зависит от Data_Adapter (передача данных в JS) и Selection_Engine (косвенно — через кеш); регистрирует шорткод.
   9. [selector-template.php] → HTML-скелет. Создаётся после определения всех данных, которые он отображает (из Data_Adapter).
   10. [assets/js/selector.js + assets/css/selector.css] → Интерфейс. Финал, так как требует готового API (AJAX_Handler), данных (Data_Adapter) и DOM-структуры (template).

**ЯВНЫЕ ЗАПРЕТЫ ВЫЗОВОВ:**
- ❌ Selection_Engine → Data_Adapter (расчёты ≠ UI)
- ❌ Data_Adapter → Selection_Engine (адаптация ≠ вычисления)
- ❌ AJAX_Handler → Data_Adapter (транспорт не знает об адаптации)
- ❌ Shortcode → Selection_Engine (HTML не знает формул)
- ❌ Template → Любой класс (чистое отображение)

6. КОНТРОЛЬНЫЕ ТОЧКИ
    КТ-1: [class-selection-engine.php] → Азофоска [16,16,16] vs Томаты/цветение [1,1,2] → 83%  
    КТ-2: [class-selection-engine.php] → Порог 75% соблюдён: результат содержит только удобрения ≥75%, либо fallback-режим (3 лучших) с флагом `'fallback' => true`  
    КТ-3: [assets/js/selector.js] → Instant Preview (<100мс): предзагруженные данные, расчёт эвристики Отиаи, маркировка «Preview»  
    КТ-4: [class-ajax-handler.php] → AJAX-ответ = точное совпадение с ручным расчётом Selection_Engine

7. КЛЮЧЕВЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ
   **Почему алгоритм Отиаи ТОЛЬКО в Selection_Engine:**  
   Это единственный источник истины для соответствия NPK. Любой другой слой, вычисляющий совпадение, создаст рассинхронизацию и сделает систему непредсказуемой.  
   
   **Почему Instant Preview — исключение из правила:**  
   Preview — это UX-эвристика, а не бизнес-логика. Её результат всегда перезаписывается серверным расчётом, не сохраняется и не влияет на смежные системы. ADR-2024-001 явно разрешает такие клиентские оптимизации при маркировке «Preview».  
   
   **Почему Fallback — архитектура, а не баг:**  
   Отсутствие удобрений ≥75% — штатная ситуация. Система не должна показывать пустой экран. 3 лучших варианта с явным флагом «fallback» — это контролируемое поведение, дающее пользователю прозрачность и выбор.

### B.2. JavaScript (UI) — UX логика без бизнес-логики

JavaScript:
- ✅ **МОЖЕТ ДЛЯ UX:**
    - определять **предварительный `state`** по правилам п.4.3
    - сравнивать концентрацию с диапазонами для определения предварительного `state`
    - выполнять **упрощённый расчёт массы** для мгновенного отображения
    - интерполировать цвет внутри `state.range`
    - отображать предварительные данные до получения ответа сервера

- ❌ **НЕ ИМЕЕТ ПРАВА:**
    - изменять алгоритм определения `state` (правила п.4.3)
    - игнорировать финальный `state` с сервера
    - быть источником истины для финальных данных
    - принимать решения о безопасности

**Разрешённая логика для мгновенного UX:**
```js
// Для определения предварительного state (те же правила что и сервер)
function getPreviewState(concentration, profile) {
    for (let state of profile.states) {
        if (concentration >= state.range[0] && concentration < state.range[1]) {
            return state;
        }
    }
    return profile.states[profile.states.length - 1]; // последний state
}
```

#### C.1. Источники состояния

- **ФИНАЛЬНЫЙ `state`** ВСЕГДА определяется:

    - только на сервере
    - является источником истины для всех итоговых данных

    - предварительный `state` для мгновенной обратной связи
    - финальный `state` как подтверждённый результат

❌ Игнорирование финального `state` — ошибка реализации

**ПЛОХО (race condition):**
```javascript
// Новый запрос не отменяет предыдущий
```

**ЛУЧШЕ:**
```javascript
let controller = null;

async function sendRequest() {
    if (controller) controller.abort(); // Отменяем старый
    controller = new AbortController();
    
    fetch(url, { signal: controller.signal });
}
```
